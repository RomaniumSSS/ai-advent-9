# Day 19 — проверка реальной модели и формулировок

Проверка выполнена локально 27.09.2026: DeepSeek V4.1 Flash через OpenRouter,
закреплённый DeepInfra, настоящий локальный stdio MCP-сервер. Модель получала
каталог трёх инструментов на каждом ходе. Подробности каждого запуска — в
[`runs.jsonl`](runs.jsonl) и [`traces/`](traces/); исходные выборки из сохранённого
реального RSS и их SHA-256 — в [`fixtures/`](fixtures/). Синтетическими были
только пустой и повреждённый RSS. Отдельно выполнены два чтения текущего RSS
из сети: [`live_feed-1`](traces/live_feed-1.json) и
[`live_feed-2`](traces/live_feed-2.json).
Основное [видео](../demo/day19-live-agent.mp4) — прямая запись отдельного
[реального CLI-прогона](../demo/live-screen-trace.json) после серии из 45
оценочных запусков: три вызова MCP с потоковыми событиями [stdout](../demo/live-screen-cli.jsonl),
два подтверждённых случая, исходные URL и сохранённый файл. Стоимость этого
дополнительного прогона $0.0018586568 не входит в сумму серии ниже.
[Слайдовая визуализация](../demo/day19-three-mcp-tools.mp4) и
[HTML-показ](../demo/evidence.html) сохранены отдельно. Прежний
демонстрационный файл оставлен только как исторический trace: его вывод
«применение не описано» оказался слишком широким после чтения полных статей.

## Объём и проверка файлов

- 45 запусков с реальной моделью по 12 сценариям и двум сетевым запускам:
  39 `saved`, 2 корректных `no_data`, 4 `failed`. Сумма сообщённого провайдером
  `usage.cost` — **$0.076889**. Это фактическая сумма этой серии, а не прогноз.
- Три отказа `mcp_call_limit` пришлись на ранние итерации широкого и смешанного
  сценариев; четвёртый отказ — повреждённый RSS. Ни один отказ не создал файл
  успешного отчёта. Последние два повтора пяти сценариев после уточнения
  инструкции дали 10/10 `saved`; один широкий повтор и оба повтора компании
  потребовали корректировки draft. Это показатель только данной выборки.
- [`audit.py`](audit.py) независимо проверил все 45 trace: `batch_id` первого
  вызова входит в аргументы второго, все `observation_id` снимка обработаны,
  `preview_id` и SHA-256 второго входят в третий, hash файла совпадает, ссылки
  взяты из исходного `model_seen`, лимиты не превышены. На прогонах без `saved`
  файл с соответствующим `run_id` отсутствует.
- Офлайн-проверки с fake provider и настоящим MCP-сервером: **15/15 OK**.
  Они проверяют контракт и сбои, а не смысл статей. Их нельзя смешивать с
  результатами DeepSeek.

## Как изменилась точность на конкретных задачах

| Сценарий | Наблюдение до исправления | Повтор после исправления |
| --- | --- | --- |
| DBA, [1086740](https://habr.com/ru/articles/1086740/) | 3/3 раза реальный агент ошибочно назван «возможным»; до 5 MCP-вызовов | 2/2 подтверждённый, по 3 вызова |
| Фильм, [1086766](https://habr.com/ru/articles/1086766/) | 3/3 раза «возможный» вместо выполненной личной задачи | 2/2 подтверждённый, одна корректировка неподтверждённой метрики |
| B2B-портал и тестовые БД, [1085712](https://habr.com/ru/articles/1085712/) / [1085576](https://habr.com/ru/articles/1085576/) | Портал 2/2 раза ошибочно «возможный» | 2/2: оба подтверждены, указаны боевой портал и тестовые БД |
| Мнение и инструкция | 3/3 раза не выданы за реальные кейсы | Повтор 1/1 без ложных ссылок |
| Смешанный RSS | Сохранял два реальных случая как «возможные» | Последние 2/2: оба подтверждены; мнение отсеяно, запуск инструмента не подтверждён как работа агента |
| Широкий RSS | 2 сохранения с пропуском кейса агентной разработки | Последние 2/2 сохранены с двумя подтверждёнными кейсами; между итерациями были два честных отказа по лимиту |
| Пустой / повреждённый RSS | — | Пустой полный поиск 2/2 `no_data`; повреждённый 1/1 `failed`, без отчётов |
| Запуск инструмента / QA-выдержка / компания с агентным кодом | — | По два повтора: нет ложного подтверждения запуска MCP-сервера, QA осторожно помечен по RSS, агентная разработка подтверждена |

Причина ранних ложных отрицаний: проверка принимала несколько общих слов
«запустили/используют», но не связывала с агентом конкретные действия
«обрабатывает тикеты», «написал фильм», «нашёл сбой», «пишут код». Изменённая
проверка привязывает действие к агенту внутри одного поля RSS и не считает
запуск сервера *для* агентов доказательством работы самого агента. Метрика
из одного заголовка теперь не проходит: текст числового результата должен
дословно находиться в RSS-выдержке. Для краткого пересказа допускается
эквивалентное написание порядкового числительного словом и цифрой.

## Остаточный риск

Агент получает `title` и до 600 символов `rss_excerpt`, а не полный текст.
Поэтому проверка формулировок **по полной статье** может обнаружить пропущенные
подтверждения даже тогда, когда отчёт честно ограничен RSS. Точность на всём
Хабре и вероятность стабильного прохождения любого широкого RSS этим набором
не доказаны. Если понадобится именно обзор полных статей, сначала нужно отдельно
согласовать и реализовать получение полного текста с новым источником
доказательств; текущий отчёт не следует выдавать за такую проверку.

Повторить локальные проверки из корня репозитория:

```bash
uv run python -m unittest day19.test_offline day19.test_report_evidence -q
uv run python -m day19.evals.audit
```

Новый реальный прогон с сохранённым RSS и отдельными файлами запуска:

```bash
uv run python -m day19.evals.runner mixed_fact_noise wide_rss --start-repeat 8 --repeat 8
uv run python -m day19.evals.audit
```

Команда `runner` требует `OPENROUTER_API_KEY` в защищённом `day19/.env` и
выполняет оплачиваемые вызовы. Для проверки уже сохранённых артефактов ключ
не нужен. В trace и журнал ключ не сохраняется.
