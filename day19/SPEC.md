# Day 19 — три инструмента одного MCP-сервера

Статус: **согласована, v0.2; правила доказательств уточнены по результату live-аудита**. Основа: задание Day 19, уточнения в
корневом `HANDOFF.md` и работающий агент Day 18.

## Цель и границы

По запросу «собери сводку о применении ИИ-агентов из RSS Хабра и сохрани её»
агент сам вызывает инструменты одного локального MCP-сервера. Результат поиска
определяет аргументы обработки; результат обработки определяет вызов сохранения.
Успех — проверенный файл с краткой сводкой и ссылками на исходные записи RSS.

Day 19 живёт только в `day19/` отдельной ветки и не импортирует код `day18/`:
переносим необходимые идеи и проверки, сохраняя самостоятельность дня. Day 18,
его cron, SQLite и VPS не меняются. Первый сценарий Day 19 запускается локально
вручную; Telegram и расписание в нём не задействованы. Этот объём и хранение
состояния в SQLite пользователь подтвердил до реализации.

## Инструменты и передача данных

Все три инструмента объявлены **одним** локальным stdio MCP-сервером. Сервер
хранит batch и подготовленный отчёт в SQLite: клиент Day 18 открывает новое
MCP-соединение на каждый вызов, поэтому состояние нельзя держать только в памяти.
У каждого инструмента узкая JSON-схема, структурированный результат и код ошибки.

| Инструмент | Что получает от модели | Что делает сервер | Что возвращает |
| --- | --- | --- | --- |
| `collect_habr_agent_cases` | Контекст запуска и фиксированного RSS-профиля, как в Day 18 | Читает RSS, сохраняет batch и снимок списка для модели | `batch_id`, статус источника, охват, `model_seen` до 20 записей с `observation_id`, выдержкой и URL |
| `prepare_report_preview` | `run_id`, **`batch_id` из первого observation**, draft классификаций и сводок с `observation_id` | Загружает снимок `model_seen` этого batch, сверяет ID и проверяемые claims с RSS, применяет проверки draft из Day 18, строит и сохраняет текст отчёта | `preview_id`, `sha256` текста, статус, исходные URL и краткое описание результата |
| `save_report` | `run_id`, **`preview_id` и `sha256` из второго observation** | Загружает сохранённый обработанный текст, сверяет hash и атомарно записывает его | Статус, серверный относительный путь, hash файла |

`prepare_report_preview` обрабатывает данные первого инструмента: модель
формулирует draft по увиденным кандидатам, а сервер проверяет опору на исходные
записи и формирует итоговый текст. Второй инструмент не делает скрытого вызова
LLM. `save_report` берёт обработанный текст по `preview_id`; модель не передаёт
ему ни произвольное содержимое файла, ни путь. URL в файл подставляются только
из сохранённых сервером записей RSS, максимум две ссылки, с различением
подтверждённых и возможных кейсов по правилам Day 18.

`model_seen` — неизменяемый упорядоченный снимок, привязанный к **текущему**
`batch_id`: сначала до 15 новых подходящих записей, затем до 5 старых
необработанных записей **из собственной базы Day 19**; свободные места
заполняются доступными записями, общий предел — 20. Старые записи могут иметь
другой `first_batch_id`, но их `observation_id` явно входят в снимок текущего
batch. Сервер сохраняет этот снимок вместе с batch; первый observation показывает
модели ровно его. Второй инструмент проверяет, что draft содержит ровно один
entry на каждый `observation_id` снимка и не содержит посторонних ID. Число
непоказанных подходящих записей и неполный охват указываются отдельно. В старую
очередь возвращаются подходящие записи, не показанные в сохранённом отчёте;
показанные и обоснованно отклонённые как нерелевантные повторно не выбираются
только после успешного сохранения. Сбой до него не расходует очередь.

Это контракт Day 19: в Day 18 первый инструмент отдаёт максимум 10 candidates,
а список до 20 собирает harness отдельным запросом. Здесь выбранный список
передаётся модели в первом observation, чтобы следующий tool call действительно
строился по нему. Автоматическая проверка устанавливает принадлежность ID и URL,
наличие указанных полей evidence, точное присутствие текста заявленных метрик
в `rss_excerpt` и базовые признаки категории по правилам Day 18. Для
`confirmed_described_case` действие должно быть связано с агентом в одном поле
источника: запуск MCP-сервера *для* агентов сам по себе не является таким
доказательством. Числа в кратком summary берутся из выдержки RSS; написание
порядкового числительного цифрой и словом считается равнозначным.
`metric_claims` требуют цифру и допустимы только для `confirmed_described_case`:
число из контекста возможного
кейса нельзя выдавать за результат работы агента. Семантическую точность свободного
пересказа оцениваем отдельно по исходным выдержкам при реальном прогоне.
Полный текст статьи не входит в observation модели; при аудите сравниваем с ним
готовые формулировки и явно указываем случаи, которые короткая RSS-выдержка
не позволяет подтвердить.

Разрешённый каталог содержит только эти три инструмента. Реальный вывод пишется
только под `day19/output/`; имя файла сервер выводит из `run_id`. Сервер
проверяет границу каталога и symlink, а запись делает через временный файл и
атомарное переименование. Тесты используют временный изолированный каталог.

## Агентный цикл и состояние

Агент получает запрос и схемы всех трёх tools, вызывает DeepSeek V4.1 Flash с
`tool_choice=auto`, проверяет предложенный вызов, исполняет его через MCP и
возвращает **соответствующий этому call ID** observation в историю модели.
Затем модель снова видит каталог и сама выбирает следующее действие. Harness
не содержит переходов вида `search → summarize → save`, не подставляет
`batch_id`/`preview_id` в вызовы модели и не вызывает эти tools сам по порядку.
Контекст запуска, включая `run_id`, создаёт harness; сервер сверяет его в каждом
вызове. Для причинной цепочки допускается один предложенный tool call за ход;
если модель предложила несколько сразу, каждый получает отказ-observation.
Предусловия проверяет сервер: обработка без своего batch и сохранение без
валидного preview дают ошибку. На каждое предложение модели, в том числе
отклонённое, возвращается структурированный observation.

Предлагаемая минимальная сохранённая стадия запуска в SQLite:
`created → data_ready → preview_ready → saved`, отдельно `no_data` и `failed`.
Она нужна для связи вызовов при повторных stdio-соединениях, идемпотентности и
разбора сбоя записи. Цена решения — таблицы переходов и проверки повторного
вызова; пользователь согласовал этот минимальный набор стадий. Ограничения:
максимум **5 MCP-вызовов** и
**6 вызовов модели** за запуск, лимиты размера аргументов и observations.
Отказ, таймаут и исчерпание лимита не превращаются в `saved`.

`no_data` допустим только если источник прочитан с полным охватом, снимок
`model_seen` пуст и общее число подходящих записей в текущем поиске и старой
очереди Day 19 равно нулю. Если записи есть, но не поместились в бюджет,
запуск завершается с `budget_exhausted`. Пустой список
при частичном охвате или ошибке источника даёт `failed` с причиной
`source_incomplete`/`source_error`, не утверждение «материалов нет». При
частичном охвате или непоказанных подходящих записях разрешён лишь отчёт с
явной меткой неполноты. Неверные аргументы, неизвестный ID, недоказанный claim,
ошибка обработки или отказ файловой записи дают код ошибки; после исчерпания
лимита запуск становится `failed`. Повторный `save_report` с теми же проверенными
данными не создаёт второй отчёт. Раннее заявление модели «готово» не считается
успехом: завершение `saved` возможно только после проверки файла сервером.

## Модель и стоимость

Первая реализация и **все реальные модельные прогоны для сдачи** используют
`deepseek/deepseek-v4.1-flash` через OpenRouter, только `deepinfra`, без fallback
и SDK retry. Профиль модели задаёт ID, провайдера, параметры reasoning, лимиты
токенов и бюджет; его выбирают **один раз перед запуском**, не между вызовами
инструментов. Агентный цикл, схемы tools и проверки не зависят от имени модели.
Позже можно добавить явный профиль Qwen и прогнать тот же сценарий, не меняя
MCP-сервер. Активация Qwen с другим провайдером потребует отдельного изменения
правила закрепления `deepinfra` в проекте; работоспособность Qwen в рамках
Day 19 сейчас не заявляется.
Перед платным запуском оценивается верхняя граница стоимости, после него в
trace сохраняется фактический `usage.cost`, если провайдер его вернул.

## Проверки и доказательства

1. Офлайн-тесты с управляемым fake provider и настоящим локальным MCP-сервером
   на RSS fixture: успешные три вызова; два разных снимка с разными
   `batch_id`/`observation_id` меняют аргументы второго вызова; `preview_id`/hash
   второго появляются в третьем. Проверить восстановление снимка с новой и
   старой записью из базы Day 19 по текущему `batch_id`, точное покрытие всех
   видимых ID, содержимое файла, исходные URL и совпадение hash.
2. Негативные офлайн-проверки: пустой **полный** поиск → `no_data`, пустой
   **неполный** поиск → `failed`, непустой неполный поиск → отчёт с меткой
   неполноты; неверный JSON/схема, чужой batch и preview, неподтверждённый
   числовой claim, ошибка обработки, отказ записи, повторный save и лимит
   вызовов. Ни один сбой не создаёт успешный отчёт. Отдельно проверить, что
   два тестовых профиля с разными ID/параметрами передаются в один и тот же
   агентный цикл без изменения его кода, а неизвестный профиль отвергается до
   сетевого вызова; Qwen для этого теста не вызывается.
3. После них — **ограниченный** прогон с настоящим DeepSeek и настоящим
   локальным MCP-сервером. Сохранить безопасный trace всех трёх вызовов с
   ID, аргументами, статусами, временем и usage без секретов и скрытого
   reasoning; независимо прочитать созданный файл, сверить URL с исходным
   снимком и **каждое опубликованное утверждение** с title/RSS excerpt. Если
   утверждение не подтверждается, прогон не считается успешным доказательством
   сдачи. Зафиксировать источник данных: live RSS или сохранённый реальный RSS
   fixture. Утверждать только то, что показал конкретный прогон.
4. Снять короткое видео: запрос → автоматические вызовы → файл и его ссылки.
   В `day19/README.md` дать команды для офлайн-тестов, реального прогона и
   просмотра результата; явно разделить fake provider и реальную модель.

Критерий сдачи: код, README, безопасный trace, проверенный файл и видео
показывают один успешный проход из **трёх выбранных моделью MCP-вызовов**
одного сервера. Коммит, push и деплой выполняются только по отдельному
указанию.
