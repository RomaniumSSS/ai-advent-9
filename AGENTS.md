# ai-advent-9 — модели для разработки

Применять к заданиям AI Advent Challenge в этом репозитории.
Технические границы проекта — в [CLAUDE.md](CLAUDE.md), текущая работа — в
[todo.md](todo.md) и [HANDOFF.md](HANDOFF.md). Эти правила дополняют общие инструкции.

## Распределение ролей

Предпочтение пользователя, зафиксировано 08.10.2026:

| Роль | Предпочтительные модели |
| --- | --- |
| Требования, спецификация, архитектура и план | Opus / Astra |
| Реализация, тесты, документация по готовому коду | Sol / Sonnet |
| Первое независимое ревью по спецификации | Luna / Haiku |
| Обязательное повторное ревью ошибок и исправлений | Opus / Astra — самая сильная доступная модель выбранного провайдера |

Пара означает альтернативы провайдеров: выбирать одну доступную модель.
При делегировании задавать её через фактический параметр модели инструмента;
название в тексте задания само по себе модель не переключает. Версию выбирать
из доступных идентификаторов. Если нужная модель недоступна, явно назвать
выбранную замену и продолжить разрешённую работу; не приписывать ей другую модель.
Не пополнять API-баланс и не подключать платного провайдера без разрешения.

Luna/Haiku проверяет соответствие спецификации, логику, обработку ошибок и тесты.
После первого ревью всегда проводить второе на Opus/Astra, даже если Luna/Haiku
не нашла ошибок. Сильный reviewer получает спецификацию, изменённый код,
замечания первого reviewer, исправления и фактические результаты проверок.
Он проверяет обоснованность замечаний, исправление ошибок, регрессии и возможные
пропуски; не подтверждает выводы первой модели без самостоятельного чтения кода.
Исправления выполняет Sol/Sonnet; после новых исправлений повторно проверять
затронутые места и связанные тесты. Недоступное обязательное второе ревью
не отмечать завершённым. Положительное заключение не заменяет свежих проверок.

При разрешённой параллельной работе давать исполнителям отдельные файлы и контексты;
зависимую реализацию вести по зафиксированной спецификации. Ревью выполнять
независимо от автора кода. Не создавать команду агентов ради простой правки текста.

Сравнивать общие затраты вместе с проверками, повторными попытками и исправлениями.
Сохранять фактическую модель роли и доступные метрики в существующем журнале задания;
стоимость и usage не выдумывать. Эффективность этой схемы ещё не измерена.
Более позднее указание пользователя имеет приоритет.
