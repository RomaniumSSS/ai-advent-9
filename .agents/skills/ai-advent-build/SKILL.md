# Реализация дня AI Advent

Адаптация [feature-builder Ивана Щитова](https://github.com/ivanshchitov/tabletop-ai-assistant-tui/blob/00a46120b5ebc816e2fe1e77ca2079abc7d1a39c/.agents/skills/feature-builder/SKILL.md).
Исходная MIT-лицензия сохранена в [LICENSE](LICENSE). Область применения — только этот проект.

## Модели по ролям

Прочитать проектный [AGENTS.md](../../../AGENTS.md): спека и план — Opus/Astra,
реализация, тесты и документация по коду — Sol/Sonnet, первое независимое ревью —
Luna/Haiku, обязательное повторное ревью ошибок и исправлений — Opus/Astra.
Выбор доступной модели определён там; не дублировать
маршрутизацию и не выдавать имя из prompt за фактически выбранную модель.

## Спецификация до кода

1. Проверить фактический корень, ветку и рабочие изменения; прочитать применимые инструкции,
   текущие разделы `todo.md` / `HANDOFF.md`, затем условие дня и затронутые файлы.
   Условие брать из сообщения пользователя или указанного экспорта, сохранять ссылку/ID сообщения.
2. Найти существующую спецификацию и подробный список задач этого дня. Дополнять их,
   не создавать второй источник требований. Для нового самостоятельного дня использовать
   `dayNN/SPEC.md` и `dayNN/TASKS.md`; OpenSpec нужен только если он уже выбран для этой задачи.
3. Спецификация должна помещаться примерно на один экран: результат для пользователя,
   включённые изменения, критерии приёмки, зависимости, проверки и существенные ограничения.
   Сохранить обязательные пункты условия. Отдельно назвать дополнительные пожелания.
   Для задания с видео сценарий из `ai-advent-deliver` входит в тот же пакет согласования.
4. **До реализации получить подтверждение этой спецификации.** Показать файл и объяснить,
   что это граница выбранного процесса: пользователь сначала проверяет, что будет построено.
   Уже данное подтверждение этой же спецификации сохраняется между ходами и сессиями.
   Исправление опечатки или уточнение внутри согласованного результата не требует нового стопа;
   изменение результата, расходов или внешних действий требует согласовать только эту разницу.
   Пока подтверждение ожидается, разрешены чтение и независимые проверки среды.

## Изоляция и параллельная работа

- Новый день начинается от объединённого `main`, в своей ветке и отдельном `git worktree`.
  Не переключать ветку в папке другого работающего агента; не убирать пользовательские изменения.
  Если навыки ещё не закоммичены, передать их проверенные файлы в новую папку отдельно:
  worktree от `main` сам по себе не содержит незакоммиченные файлы основной папки.
  Вместе с ними передать проектный AGENTS.md и относящиеся к ним изменения CLAUDE.md,
  если они ещё не входят в базовый commit. Перед копированием сверить назначение;
  существующие отличающиеся инструкции не перезаписывать без разбора.
- Пример имён: ветка `day27-local-app`, соседняя папка `ai-advent-9-worktrees/day27`.
  Сначала проверить, что эти имена свободны. В новой папке снова проверить инструкции и статус.
- Параллельная разработка нескольких дней допускается, когда пользователь выбрал такой запуск
  и задачи независимы. Каждый исполнитель получает условие, согласованную спецификацию,
  свой worktree, список разрешённых файлов, входные данные и критерии завершения.
  Папка дня, порт, результаты, SQLite и временные данные должны быть отдельными.
- Общие `README.md`, `todo.md`, `HANDOFF.md`, зависимости и lock-файл объединяет один ответственный
  после проверки изменений дней. Не поручать нескольким исполнителям править их одновременно.
- Существующий корпус и индекс можно читать совместно как неизменяемый снимок.
  Не менять индекс, модель embeddings или приватное состояние сданного дня ради нового задания.
- На этом Mac 16 ГБ RAM: реальные LLM-прогоны и записи видео выполнять последовательно.
  Не перезапускать общий Ollama и не выгружать модель, пока она используется другим прогоном.
  Подготовка кода может идти параллельно с генерацией. Day29 сравнивает с сохранённой исходной
  версией; измерения оптимизации начинаются после получения исходных результатов.

## Реализация и проверка

- Для нового значимого поведения: воспроизвести требование падающим тестом, проверить причину
  падения, реализовать минимальное изменение и получить зелёную проверку. Использовать
  существующий тестовый инструмент дня; не устанавливать pytest только ради этого навыка.
  Для документации и простых визуальных правок достаточно целевой проверки.
- Тестировать контракт: историю чата, обработку ошибок, ограничения локальных адресов,
  фактическую передачу запроса и ответы. Не закреплять случайную формулировку LLM как эталон.
  Моки проверяют обвязку; работа реального провайдера и качество ответа проверяются отдельно.
- В ходе работы запускать затронутые проверки; расширять набор при найденной зависимости
  или регрессии. Старые платные замеры и весь набор Day01–26 автоматически не повторять.
- Повторная неудача без новой гипотезы — повод собрать воспроизведение и выяснить причину.
  Не менять критерий приёмки, чтобы объявить неудачный ответ успешным.
- Платный прогон использует только явно разрешённый бюджет. Нет актуального разрешения —
  выполнить офлайн-часть и обозначить, какая реальная проверка ещё нужна.
- Свежие результаты и подробное выполнение хранить в каталоге и трекере дня. После смыслового
  результата кратко обновить `todo.md`: результат, доказательство, следующий шаг и блокер.

## Передача результата

Проверить итоговый diff относительно исходного состояния. Указать, что реализовано,
какие проверки прошли, где использовались моки и что осталось непроверенным.
Изменения сданных дней и данные пользователя не включать в коммит нового задания.

Коммит, push, merge, тег или публикация выполняются только в пределах настоящего разрешения
пользователя. Если его нет, сначала подготовить проверенный diff и конкретный список действий,
затем запросить недостающее разрешение. Уже разрешённое действие повторно не согласовывать.
Не навязывать fast-forward, rebase, теги, удаление веток или GitHub Release как условия выполнения.
Ссылки прежних сдач сохранять при интеграции. Наличие кода и зелёных тестов не означает «сдано».
