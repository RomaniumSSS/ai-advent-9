# День челленджа: код, живая запись и материалы сдачи

Адаптация [solve-challenge-task Ивана Щитова](https://github.com/ivanshchitov/tabletop-ai-assistant-tui/blob/00a46120b5ebc816e2fe1e77ca2079abc7d1a39c/.agents/skills/solve-challenge-task/SKILL.md).
Исходная MIT-лицензия сохранена в [LICENSE](LICENSE).

Распределение моделей для разработки и ревью брать из проектного
[AGENTS.md](../../../AGENTS.md). Сценарий, скрипт записи и release notes по готовой
реализации относятся к работе Sol/Sonnet; саму локальную модель приложения
эта настройка не меняет.
Перед итоговой проверкой и сдачей выполнить оба ревью из AGENTS: Luna/Haiku,
затем обязательное Opus/Astra по ошибкам, исправлениям и возможным пропускам.

## Подготовить один пакет согласования

Прочитать [ai-advent-build](../ai-advent-build/SKILL.md) и выполнить его подготовку.
К спецификации дня добавить сценарий `dayNN/video/SCENARIO.md`: начальное состояние,
видимые действия и доказательство каждого обязательного результата. Для долгой локальной
генерации заложить фактическое ожидание; длительность не назначать вместо измерения.
Пользователь согласует спецификацию и сценарий вместе. Второе подтверждение той же спеки
при вызове `ai-advent-build` не нужно. Если разрешён пакет нескольких дней, сохранить
согласованные границы и зависимости каждого дня.

## Реализовать приложение

Выполнить `ai-advent-build` в папке дня. Перед съёмкой должны работать именно сценарии,
которые будут видны в видео. Снимать можно с проверенной рабочей ветки; предварительные
merge в main, push, тег или релиз для съёмки не требуются.

## Автоматизировать и провести сухой прогон

- Подготовить повторяемый скрипт сценария для этого дня: например,
  `dayNN/video/run_demo.py`. Использовать его же действия для записи.
  Разделить режимы без записи и с записью, сохранить времена шагов и результат проверок.
- Создать новый каталог данных и результатов для каждого прогона. Использовать те же
  настройки модели и снимок индекса, что планируется показывать. Не перемещать и не
  очищать пользовательскую историю ради красивого начального экрана.
- Ждать завершения конкретного запроса по его ID, состоянию приложения и реальным метрикам.
  Слова, напечатанные самим скриптом, эхо ввода и таймер не доказывают получение ответа.
  Таймаут выбирать по уже наблюдавшейся скорости модели.
- Сухой прогон проверяет каждый пункт сценария, отсутствие ошибок интерфейса и читаемость.
  Модельные ответы и ошибки сохраняются. Неудачный обязательный шаг сначала исправить;
  недостаток качества ответа честно отразить, даже если транспортная часть работает.
- Для демонстрации реальной модели фикстура не заменяет реальный прогон. Учесть, что сухой
  прогон и запись создают отдельные запросы: облачные вызовы должны помещаться в разрешённый
  бюджет; локальные прогоны нескольких дней выполняются по очереди.

## Записать живое выполнение

Для браузерного приложения читать [инструкцию записи](references/recording.md).
Записывать реальный viewport приложения во время новых запросов и ответов. Ролик,
собранный из сохранённого вывода, слайдов или скриншотов, не считать живой записью.
Существующие записи не перезаписывать; каждому дублю — отдельный путь.

Закрыть свой контекст записи в `finally`, дождаться завершения файла. Не останавливать
чужой браузер, Ollama или рекордер. Если доступный захват не работает, сохранить код,
прогоны и конкретную причину; обязательное видео остаётся незавершённым результатом.

Проверить:

- файл открывается, длительность и размеры получены через ffprobe;
- вручную прочитаны кадры начала, ключевых ответов и конца через просмотр изображений;
- показаны реальные действия и обязательные результаты, текст помещается в кадре;
- нет чёрных, застывших или чужих кадров, ошибок, скрывающих результат;
- число запросов и видимые метрики совпадают с журналом именно записанного прогона.

Размер кадра сам по себе не доказывает качество записи. Монтаж и ускорение ожидания
возможны только по выбору пользователя; исходную запись и реальные длительности сохранить.

## Подготовить сдачу

В папке дня подготовить код и инструкцию запуска, видео, `RESULT.md` и `RELEASE_NOTES.md`.
В заметках: проблема и новое поведение, проверки, фактические времена и токены, ограничения.
Ничего не придумывать при отсутствии метрик. Для локальной генерации не оценивать стоимость
электричества по стоимости API. Ключи, приватные сообщения и закрытый корпус не публиковать.

Дать пользователю ссылки на точные файлы. Ссылку на GitHub подтверждать существующей веткой
или коммитом; не выдавать будущий URL за уже опубликованный. Коммиты, push, merge, загрузка
видео и изменение таблицы выполняются только в пределах актуального разрешения пользователя.
Локальные артефакты подготовить и проверить до запроса недостающего разрешения.

Отдельно обозначать «код проверен», «видео проверено», «опубликовано» и «пользователь сдал».
Последнее подтверждает пользователь. Обязательное видео, оставленное ручным шагом,
не позволяет объявить весь результат «Видео + Код» готовым.
