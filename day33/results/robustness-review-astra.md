## Замечания

1. **BLOCKER, domain.py:72–89 и model.py:56–63.** Вопрос `Не могу войти, пишет неверный пароль`, пользователь alice, T101, возвращает `response_kind=model_answer`, `model=deterministic-offline-mock`, совет подтвердить почту из FAQ-EMAIL без признания отличающегося текущего симптома. Воспроизведено через `Application().ask(...)` с настоящим stdio MCP. Замечание Luna подтверждено для mock и маршрута: наличие события не доказывает, что оно объясняет нынешнюю ошибку. При этом это **не доказанная ошибка Qwen**: live SYSTEM уже требует уточнять противоречия; пропуск gate сам по себе не означает неверный live-ответ. До live проверки нельзя приписывать Qwen этот результат.

   Ограниченное исправление: обеспечить уточнение для явного сообщения о другой текущей ошибке и отдельный регрессионный пример неверного пароля; не наращивать бесконечный список симптомов/кодов ошибок. Допустима консервативная обработка сообщений с явно сообщённым текстом ошибки, без попытки универсальной классификации. Mock, который не анализирует смысл вопроса, должен обозначать событие как сведения тикета и не выдавать его за установленную текущую причину; при сомнении уточнять. Сохранить исходные два подтверждённых сценария и разговорные общие вопросы. В live holdout заранее добавить текущий конфликт и проверить ответ независимо: выяснение текущей ошибки допустимо, уверенный диагноз из старого события — нет. Не заменять эту проверку количеством зелёных mock-тестов.

2. **WARNING, domain.py:42–49,92–101.** Дополнительный `system_instruction` принимается внутри user, ticket и event и остаётся в возвращаемом контексте. Три самостоятельные мутации свежего MCP-контекста дали успешный `validate_context`. Это не продемонстрированный обход scope и не доказанная prompt injection: scope-ID проверяются, а произвольный текст уже разрешён внутри detail/subject. Но граница не соответствует заявлению о строго проверенном контракте. Малое исправление: точные наборы полей на трёх уровнях либо построение нормализованного объекта только из разрешённых полей; негативные тесты каждой вложенности. Не вводить production authentication.

3. **WARNING, live_robustness.py:14–23,43.** CLI принимает `--accounted-ceiling nan`/`inf`; сравнение с NaN не блокирует reserve. Офлайн Fake Budget при accounted=.80 и maximum=.01: .767852 → denied; nan/inf → would-reserve. Общий Budget всё ещё ограничивает $1, поэтому это не обход общего ledger, но дополнительный операторский потолок обходится некорректным числом. Проверить конечность и допустимый диапазон потолка до создания Budget; покрыть NaN/Inf отрицательными тестами. Запланированный последовательный оператор делает отсутствие атомарной проверки SessionBudget приемлемым в текущем scope; расширение архитектуры/конкурентных операторов не требуется.

## Targeted review после фактического live failure — 17.10.2026

**APPROVED для ограниченной повторной live-проверки; семантическое исправление пока NOT PROVEN.** Самостоятельно прочитаны `results/robustness-live/fresh-markerless-conflict.json`, фактические FAQ-EMAIL/FAQ-LOGIN, обновлённый SYSTEM и offline evidence. Теперь это реальный Qwen FAIL, а не вывод из mock: ответ придумал блокировку входа до проверки пароля и предложил сначала подтвердить почту, затем повторно проверить иной симптом. Ни порядок проверок, ни такая причинная связь в источниках отсутствуют; слово «может» не делает догадку обоснованной. Предыдущее failure evidence сохраняется.

Новая инструкция адресует механизм ошибки: отделяет состояние события от текущей причины, запрещает неизвестные механизмы/порядок/причинные связи (включая осторожные формулировки) и последовательность «сначала исправить событие, потом проверить другой симптом». Для конкретного симптома без явной связи в FAQ требует признать расхождение и уточнить. Для общих вопросов о входе сохраняет возможность сообщить данные тикета и соответствующий шаг FAQ с атрибуцией. Это ограниченная prompt-коррекция, без нового regex, классификатора или изменений прав/transport.
