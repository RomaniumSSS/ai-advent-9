# Day33 robustness — первое независимое review (Luna)

**Итог: NEEDS CHANGES.** Основные защищённые маршруты и транспортные ограничения проходят офлайн-проверки, но текущий gate пропускает распространённый конфликт между сообщённым симптомом и диагнозом из тикета. Модельный ответ при таких входных данных может уверенно назвать устаревшую причину.

## Замечания

🔴 **[BLOCKER] `domain.py:77-89` — текущий симптом с неверным паролем проходит как подтверждение старого `email_unverified`.** Воспроизведение: `Application().ask('alice', {'ticket_id':'T101','question':'Не могу войти, пишет неверный пароль'})` возвращает `model_answer` и FAQ-EMAIL: «При email_unverified…». Фраза не совпадает с текущим сообщением пользователя и может быть устаревшей; заданный robustness-критерий требует уточнения при противоречии, без диагноза. Добавить такой сценарий в fixtures и направлять распознанные явные альтернативные причины (например, неверный пароль/код ошибки) в уточнение либо явно ограничить ответ до общего шага, который не объявляет событие причиной. Повторить тесты и независимое review после исправления.

🟡 **[WARNING] `domain.py:23-37,92-100` — валидаторы принимают неизвестные поля.** `validate_context` строго проверяет только верхний уровень, а пользователь, тикет и события сохраняют любые дополнительные ключи; они затем попадают в полный JSON контекста модели. Например, лишнее поле `system_instruction` в событии не отвергается. Уточнить schema до точных наборов ключей на каждой вложенности и добавить malformed-context проверки для лишних полей, если контракт MCP должен быть закрытым.
