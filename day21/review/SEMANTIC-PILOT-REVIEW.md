# Пилот смыслового отбора — 10 кейсов

## Что выполнено

В разрешённой пользователем пробной подборке 47 уникальных сообщений,
57 сочетаний «сообщение в кейсе», 10 кейсов. Некоторые сообщения входят в
несколько кейсов с разным контекстом. Облачный Sol high и локальная qwen3:8b
завершили все кейсы. Результаты — предложения, активный корпус не менялся.

Локальная модель: Mac M2, 16 GiB RAM, Ollama 0.17.7, Q4_K_M,
think=false, temperature=0, num_ctx=8192, num_predict=2048.
Digest: `500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`.
Сумма времени десяти вызовов — 1164,182 секунды, около 19 мин 24 с;
включает загрузку модели внутри вызовов. После прогона модель выгружена.
У всех ответов полный охват переданных ID и нормальное завершение, но это
только структурные проверки. Время/стоимость облачного агента не измерены.

## Результаты проверки

- 31 из 57 решений совпало, 26 разошлись. Это согласие, не точность.
- Local: конкретные полезные ответы в C02/C04 исключены как второстепенные,
  хотя отвечают на включённые технические вопросы. Это потеря контекста.
- Local: в C09 включены посторонний разговор и оценочная реакция на отсутствующее
  вложение; обоснование приписывает сообщению техническую информацию, которой нет.
- Local: в C01 объединены разные вопросы под общим условием в один документ.
  В C07 в группы документов попали оба сообщения со статусом exclude.
- Обе модели неверно определяют происхождение: cloud — 11, local — 14 ошибочных
  source_role из 57. Личный опыт участника Telegram — discussion, не personal_note;
  personal_note обозначает выбранный раздел отдельной учебной заметки.
  Local дополнительно объявляет отдельные вопросы участников assignment.
- Cloud лучше сохраняет явные вопрос–ответ и разделяет ветви в просмотренных
  C01/C02/C04. Но cloud также не эталон: часть технических обсуждений откладывается
  из-за недоказанной истинности/устаревания, хотя это другая ось оценки, и допускаются
  review-записи в группах документов без явного статуса самой группы.
- C03 с идеей оценки ответов моделью и C06 с длинным примером вывода выявили
  неоднозначность правил полезности. Полезный пример вывода модели не равен
  исключаемому бот-пересказу чата. Отбирать только техническую часть сообщения
  без сохранения оригинала и происхождения сейчас не согласовано.

Это предметные наблюдения на малом наборе, не общая оценка превосходства моделей.
Разногласия по пограничным кейсам не помечены автоматически ошибками local.

## Недостатки самого эксперимента

1. Тип источника предложено угадывать по тексту, хотя он известен из происхождения.
2. Не разделены полезность, полнота контекста и достоверность технического совета.
3. Не определено, document_groups — кандидаты или только готовые к включению группы.
4. Cloud видела всю подборку в одной сессии, local — независимые кейсы.
   Промпты близкие, но не идентичные; настройки/инструменты тоже различны.
   Это сравнение рабочих схем, не изолированное сравнение моделей.
5. Выборка вручную направленная, часть кейсов пересекается. Лимиты контекста
   в генераторе (до 3 предков и до 10 сообщений) могли оборвать обсуждение.
   Нельзя переносить частоты ошибок на весь корпус или считать повторные ID
   независимыми испытаниями стабильности.

## Изменения для следующего прогона

- Передавать `source_role` неизменяемым входным полем из инвентаря/типа файла.
  Выход модели не может повысить обсуждение до условия или превратить его в заметку.
- Задача модели: релевантность и связность, а не проверка истинности каждой реплики.
  Спорные утверждения сохранять с ролью обсуждения и отдельным предупреждением;
  не превращать их в требования курса. Недоступная ссылка не является прочитанной.
- Полезные вопросы без ответа допустимы. Короткий ответ оценивать вместе с вопросом;
  благодарность и реакция без технического вклада сами по себе не нужны.
- Готовые document_groups содержат только include; review-группы отдельны.
  Для смешанного длинного сообщения — review/mixed_content, без самовольного
  переписывания или удаления частей. Исходные тексты сохраняются.
- Указывать отсутствующих родителей/ответы и явную неполноту входа. Не придумывать
  пропущенное и не считать ограниченный preview полным обсуждением.
- Проверять машинно охват ID, допустимые статусы, неизменность происхождения,
  отсутствие exclude в готовых группах и отсутствие выдуманных ID.
- Одинаковый текст задания и одинаковый набор сообщений на каждый кейс для обеих
  схем. Различия agent harness/API и режима reasoning всё равно явно фиксировать.

Сначала повторить исправленный пилот. Затем согласованные 30–50 обсуждений:
обычная выборка по периодам курса плюс трудные случаи; контрольные обсуждения
не пересекаются с настройкой по ID или ветви. Их не использовать для правки
промпта до первого контрольного результата. Не выбирать только кейсы, где
модели уже разошлись. Финальная ручная приёмка сейчас не проводится.
