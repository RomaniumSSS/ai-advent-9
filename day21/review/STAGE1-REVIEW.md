## Luna

### L1 — BLOCKER: выбор активной версии расходится с манифестом

`import_corpus.py:716,734` сохраняет старые решения, а каждую новую версию
известного условия независимо помечает `include`. Функция `accept_replacement`
на строке 536 меняет указатель в состоянии, но манифест этот указатель не учитывает.

Воспроизведено: принятое условие + исправленный импорт дают два `include`
до согласования исправления; после принятия новой версии старая остаётся
`include`. Нарушены S2/A3: ожидающая замена не должна входить в активный корпус.
Реальный текущий state дополнительно содержит 0 accepted-указателей при 24
`include` в манифесте: первоначальное принятие Telegram-записей не связано
с механизмом последующих замен.

Исправление: единый источник истины о принятом сообщении/версии; отдельно
история наблюдений и предложения. Манифест активного корпуса строить по принятой
версии, принятие/замену сохранять вместе с решением. Проверить весь путь до
перезапуска и повторного построения манифеста, а не только функцию изменения указателя.

### L2 — WARNING: формат реального заголовка нового дня не распознаётся как условие

`import_corpus.py:740`: якорный regex требует Day/День в начале строки.
Синтетический `🔥 День 25. New assignment` от проверенного автора даёт
`source_type=discussion`, хотя номер 25 извлечён. Реальные заголовки используют emoji.
Исправление: распознавать префикс реального формата, добавить этот случай в тест.

### L3 — WARNING: независимая от пользователя часть этапа ещё не завершена

`main` на строке 1015 предоставляет только импорт. Нет рабочего пути записи
решений отбора/принятия версии через CLI и сборки документов обсуждения/отчёта
объёма. Функция принятия возвращает изменённый dict, но не соединена с сохранением
и манифестом. Эту инфраструктуру можно закончить на синтетике без просмотра чата.
Ожидание смысловых решений не объясняет всю оставшуюся работу.

Отдельно: «interrupted recovery» в test_import.py:258 сохраняет JSON успешно,
потом перечитывает его. Это не имитация исключения при записи комплекта файлов
в import_snapshot:995–1000. Атомарность отдельного файла не доказывает
согласованность state/manifest/note при сбое между записями. Добавить реальный
отказ в этом промежутке и проверку восстановления; не объявлять текущий тест
доказательством этого свойства.

## Sol

### S1 — BLOCKER: вложенные метаданные пересылки становятся метаданными сообщения

`corpus.py:127,140`: `first_class` ищет по всему поддереву. Если у внешнего joined
сообщения нет from_name, имя берётся из forwarded и становится last_author для
следующей реплики. Вложенный reply также считается внешним.

Воспроизведено: внешний автор Outer → joined-пересылка Forwarded → joined-реплика
дают Forwarded у двух последних сообщений; reply пересланного источника 999
становится ребром обсуждения. Это искажает происхождение и группировку корпуса.
Исправление: разделить внешний body и forwarded; наследовать только допустимые
внешние метаданные, хранить forwarded reply отдельно без ребра текущего чата.

### S2 — BLOCKER: первая версия заметки теряется после принятия исправления

`corpus.py:366` заменяет accepted.record_json. Telegram-версии остаются в
observations, но исходная заметка туда не записывается; proposals содержит
только последующие версии. После First note → Second note → accept-proposal
First note отсутствует во всех таблицах содержимого. Нарушено сохранение
предыдущих версий S2.

Исправление: хранить все версии заметок до переключения активной ссылки;
повторное открытие должно позволять восстановить первую принятую версию.

### S3 — BLOCKER: манифест смешивает принятую версию с метаданными непринятой

`corpus.py:415–422`: accepted_hash берётся из accepted, а source/reply — из
latest_json. При новой непринятой версии с изменённым reply манифест уже
показывает новый reply. Воспроизведение: принятый 7001, исправление 7002;
манифест сообщает 7002 до решения пользователя. Сами документы пока используют
accepted, поэтому они расходятся с манифестом происхождения.

Исправление: для include брать текст и метаданные одной принятой версии;
метаданные предложения показывать отдельно с его хешем/статусом.

### S4 — WARNING: приватный preview рендерит исходный Markdown

`corpus.py:471` вставляет текст сообщения напрямую. При открытии в Markdown-viewer
с разрешёнными внешними изображениями содержимое может инициировать сетевой
запрос. Это риск, обнаруженный чтением кода; фактическая утечка не проверялась
и не утверждается. Сделать исходный текст инертным: безопасный code fence
с учётом backticks внутри либо экранированный локальный HTML без внешних ресурсов.

## Общие ограничения и сравнение

- Обе реализации честно оставили 3467 сообщений на просмотр. Это полный
  предварительный учёт, но не выполненный тематический отбор. Родитель дал
  одинаковое ограничение не выводить переписку в модельный контекст: оно
  ограничивает смысловую проверку обеих моделей и не считается их ошибкой.
- Минимум 30 страниц ещё не доказан. Sol построила документы и оценку для
  24 условий + заметки; Luna сохраняет заметку отдельно и не строит итоговые документы.
- 113 расхождений старых text-hash у Luna требуют локальной сверки. Само
  расхождение с прежним парсером не доказывает потерю текста. Его verifier PASS
  не доказывает правильность этих фрагментов: расхождения не входят в проваленные gates.
- У Luna после замечания родителя исправлена путаница forwarded reply. Sol
  этого замечания во время разработки не получала: результаты нельзя представлять
  как полностью слепой контролируемый benchmark. Это сравнение двух рабочих попыток.
- У Sol больше законченных операций: SQLite-транзакции, CLI решений, сборка
  документов/объёма. Однако сохранность версии заметки и происхождение нарушены.
  Sol удобнее рассматривать как кандидата на основу после исправлений;
  оснований принять её сейчас или назвать модель безусловно лучше нет.
- Число тестов не равно качеству: все авторские тесты прошли при наличии этих ошибок.
  Время прогона моделей и токены/стоимость достоверно не измерены; capacity error
  Sol учитывается как доступность, не дефект написанного кода.
