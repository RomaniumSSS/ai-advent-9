# Day30 — сценарий живой записи

Один сценарий `run_demo.py --mode dry|record`, три новых последовательных запроса
в каждом режиме. Только отдельный server-side `assignment` сервис, существующий
frozen index и profile12 Qwen3 8B Q8/8192. Старые разговоры, runtime и модель
не сбрасываются. Dry и record создают суммарно шесть новых принятых запросов.
При runtime error, timeout или unknown прогон прекращается; сохранённые ошибки
не подменяются ответами и не запускается retry или настройка качества.

Скрипт проверяет HTTPS CA и hostname Python-клиентом до Chromium. Chromium
доверяет только SPKI сертификата из `--cafile`, без `ignore_https_errors`.
Токен читается из env, вводится только в password поле и немедленно очищается;
его текст не виден в кадре и не выводится в журнал. Из env `DAY30_PRIVATE`
берётся локальный каталог `state`, чтобы сопоставить API-ответ с полным receipt.

1. Подключение к assignment-сервису; надпись «ДЕМО · только открытые условия
   заданий». Видимый блок «Проверка живого HTTP API» показывает настоящий
   `GET /api/state`: model, scope, context, rate limit и idle состояние.
2. В том же блоке показываются настоящие отказы API: отсутствие bearer token
   даёт `401 unauthorized`; вопрос из 501 символа даёт `400 invalid_request`.
   Эти запросы не запускают inference. `429/Retry-After` проверяется отдельно
   offline; на видео не заявляется реальная нагрузочная проверка шести запросов.
3. Новый разговор: «Что требуется в задании дня 21 при создании индекса
   документов?». ID берётся из конкретного HTTP `202` на нажатие «Спросить архив».
   Пока этот запрос accepted/running, второй POST получает настоящий `409 busy`;
   активный receipt и отказ сохраняются. Видны фазы настоящей генерации.
4. После `done` показаны пересказ, вывод, реальные времена/токены и раскрытый
   первый оригинал. В блоке API — точные request/conversation IDs и ограниченные
   реальные метрики: attempted/completed calls, prompt/output tokens, context
   и max output из бюджета приватного receipt. Это не benchmark и не пик RAM.
5. В том же разговоре: «Какие метаданные требуется сохранять для документов
   в этом задании?». Два хода остаются в UI; conversation ID совпадает, request ID
   новый. Ожидание, ответ, метрики и раскрытие оригинала повторяются.
6. Новый разговор: «Что требуется в задании дня 24: как показывать источники
   и когда отказываться отвечать?». Новый conversation/request ID, live ответ,
   реальные метрики, раскрытие оригинала. Итоговые разговоры перечитываются через
   HTTP API; порядок ID и terminal done сверяются без повторной генерации.
7. Закрытие собственного record context в `finally`. Сохраняется новый raw WebM;
   успешная запись конвертируется в новый MP4 без аудио и ускорения, 1280×1000.
   `ffprobe` сохраняется рядом; полный raw и неудачная запись не перезаписываются.

После каждого ответа выдерживаются паузы и прокрутка для чтения вывода,
метрик и оригинала. Root просматривает кадры начала, ключевых ответов и конца,
проверяет читаемость, воспроизведение и отсутствие приватных данных. Dry/mock
не заменяет новые ответы record. Все полные receipts, traces, screenshots,
ошибки и видео до privacy review остаются в новом приватном каталоге0700;
JSON-файлы0600. `safe-public-summary.json` содержит только assignment scope,
ID, статусы, счётчики, числа/параметры и коды отказов; он требует privacy review
перед публикацией. Prompts, source texts, токен и полный trace в него не входят.

По уточнённому SPEC качество дополнительного пересказа не является gate сдачи.
Исторический profile12 private semantic FAIL сохраняется; новые refs/валидный
JSON и runtime PASS не доказывают смысловую полноту. Ответы записываются целиком,
а фактические ограничения отражаются в итоговой документации.
