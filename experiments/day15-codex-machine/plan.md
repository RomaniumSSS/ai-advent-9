# День 15 — план реализации

## Цель и границы

Создать самостоятельный `day15/` на основе кода Дня 14. Сохранить память,
инварианты, полуавтономный workflow и SQLite. Добавить серверный контроль
переходов задачи; прежние `day01/`–`day14/` не менять. Финальное принятие
результата остаётся действием пользователя.

## Внутренняя FSM продукта

| Текущий этап | Событие и обязательное свидетельство | Новый этап |
|---|---|---|
| `planning` | утверждён сохранённый план текущей версии | `execution` |
| `execution` | результат выполнения есть и подтверждён завершённым | `validation` |
| `validation` | пользователь принял показанный результат проверки | `done` |
| `validation` | замечания пользователя сохранены | `execution` |

`pause/resume` меняет только статус и версию, не этап. `done` терминален.
Новая задача создаётся отдельным действием. Модель может предложить переход,
но применяет его только серверный шлюз. Ручной API, CLI и автоматический workflow
обращаются к одному шлюзу с условиями, привязанными к сохранённым артефактам
и версии задачи. Отказ возвращает текущий этап, причину и разрешённое действие;
состояние, история и предложение workflow не изменяются.

## Этапы работы и проверки

1. **IMPLEMENT.** Скопировать накопительный модуль в `day15/`; определить
   типизированные события, условия переходов и audit отказов. Подключить шлюз
   ко всем путям смены этапа. В UI показать текущий этап, разрешённое действие
   и причину отказа без возможности обхода через обычный чат.
2. **VERIFY.** Офлайн проверить положительный путь, `planning → validation`,
   реализацию без утверждённого плана, финал без проверки, пустой и ложный
   `submit_result`, повторное применение, устаревшую версию, возврат на доработку,
   паузу до/во время перехода и `pause → restart → resume`. Запустить регрессии
   FSM, workflow, инвариантов и web из копии Дня 15. Проверить, что старые дни
   не изменены.
3. **DEMO.** На свежей БД снять короткое видео: план → отказ в перескоке →
   утверждение → выполнение → проверка → пауза/перезапуск/продолжение →
   принятие. Указать, где использован офлайн-клиент, а где реальный провайдер,
   если он будет вызван.
4. **REVIEW.** Прочитать diff и результаты, проверить обходы через API/CLI,
   сохранение данных и точность README. Найденный дефект возвращает работу в
   IMPLEMENT с конкретной причиной и повторной проверкой затронутого пути.
5. **LIVE_VALIDATION.** По дополнительному требованию Романа до коммита прогнать
   несколько полных задач через реальный OpenRouter с закреплённым DeepInfra,
   без fallback и mock-ответов. Проверить отказ в перескоке, ревизии, паузу,
   новый экземпляр агента, восстановление, возврат на доработку и финальное
   принятие. Сохранить фактические вызовы, ответы, токены и стоимость; лимиты:
   16 вызовов и $0.02. Красный прогон возвращает в IMPLEMENT.
6. **CI после пуша.** Добавить `.github/workflows/day15.yml` с запуском на push
   ветки дня 15 и pull request: Python 3.12, установка зависимостей, офлайн-тесты
   `day15/`, проверка синтаксиса JS/Python и внешней FSM. После разрешённого
   коммита и пуша открыть конкретный GitHub Actions run и сохранить ссылку,
   conclusion и commit SHA в `day15/results/ci-report.json`. Красный run возвращает
   в IMPLEMENT; `DONE` требует зелёного run именно для опубликованного SHA.

## Готовность и ограничения

Результат: код в `day15/`, воспроизводимые проверки и видео, README с командами
и известными пределами проверки. Не считать текст модели доказательством
завершённого действия без проверяемого артефакта. Коммит, push и внесение ссылки
в таблицу не выполняются автоматически этой FSM. GitHub Actions запускается
после пуша, а не внутри локальной операции `git push`.

**Согласование:** Роман утвердил план 19.09.2026 после добавления требования CI.
Позднее Роман явно добавил длинный реальный прогон до коммита; маршрут расширен
этапом LIVE_VALIDATION с сохранением истории переходов.
Текущий этап и точка продолжения находятся в `state.json`.
