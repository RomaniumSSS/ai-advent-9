# Оценка неудачного comparison pilot — Day31

16.10.2026. Анализ: фактическая модель `gpt-6-astra`.
Только чтение сохранённых результатов, публичной документации и локальная
проверка SDK с synthetic transport; новых запросов генерации не было.

## Что установлено

В `compare-models-pilot-20261016/` девять запусков завершились ошибкой:
шесть GLM5.3/DeepSeek4.1 сохранили generation ID, но не сохранили final content,
finish_reason или usage; три Qwen3.8Max сохранили класс `NotFoundError`, без ID.
Это **FAILED/API comparison**, а не сравнение качества ответов. Оснований
ранжировать интеллект, точность или скорость нормальной генерации моделей нет.

Прочитан `diagnosis.json` Sol: все шесть GET по generation ID вернули 404;
публичный каталог по-прежнему содержит три активных endpoint с заявленной
поддержкой нужных параметров. Ни 404 metadata, ни отсутствие usage не доказывают
нулевой расход. Реальная upstream-причина и фактическое списание остаются
неизвестными. Девять удержанных резервов сохраняются. По сохранённой сводке
общий charged/reserved составляет `$0.25972282`, остаток `$0.24027718` из `$0.50`;
это состояние внутреннего ledger, **не доказанная сумма списания OpenRouter**.

## Подтверждённый пробел диагностики

Текущий адаптер извлекает id/model/provider и поля choices/usage, но не
сохраняет `response.error`; в исключении HTTP сохраняется только тип исключения,
без кода/типа ошибки из тела. Поэтому исходная причина могла быть утрачена.
OpenRouter документирует возможность ошибки внутри тела ответа после начала
обработки; успешный HTTP сам по себе не означает успешный результат.
[OpenRouter: Errors and Debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging).

Самостоятельно воспроизведено офлайн через установленный OpenAI 3.6 SDK и
`httpx2.MockTransport`: synthetic HTTP 200 с `{id,error:{code:400,message:...}}`
превратился в **ровно такой** сохранённый набор — id есть, usage/content/finish
равны null, локальный code=`incomplete`, исходный error потерян. Сети не было,
использовался временный ledger, удалённый после проверки. Это доказывает дефект
наблюдаемости, **не доказывает**, что реальные шесть ответов имели именно code400.
Моё предыдущее ревью comparison этот error-envelope не проверило.

Перед дальнейшей диагностикой полезна одна небольшая правка: сохранять
ограниченный набор upstream error code/type и HTTP status для успешного HTTP
с error-body и для SDK exception, без headers, ключей, prompt и скрытого
reasoning. Не нужен полный dump SDK или новая система журналирования.
Отклонение таких ответов и удержание резерва уже работают безопасно.

## Что нельзя объявить причиной

В новых запросах сохранены тот же механизм сообщений, strict JSON schema,
temperature=0, отсутствие fallback/retry; изменены модель, маршрут, часть
reasoning-параметров и output cap. Старая GLM4.7/Venice возвращала content и usage,
но иногда семантически обрывала текст при finish_reason=stop.

Нельзя приписать новые ошибки исчерпанию output tokens: нет finish_reason=length
или счётчиков reasoning. Нельзя доказанно обвинить effort=low: DeepSeek был
вызван с enabled=false. Нельзя считать strict schema универсально рабочей
только по metadata: поддержка и ограничения schema зависят от endpoint.
[OpenRouter: Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs).
Возможны несовместимость сочетания параметров, endpoint/account routing или
ошибка upstream; сохранённых данных недостаточно выбрать одну причину.
Провал этих маршрутов также не доказывает глобальную недоступность трёх моделей.

## Наименьший обоснованный путь к завершению

**Сохранить comparison как FAILED/API и выполнить одну ограниченную попытку
на ранее отвечавшем GLM4.7/Venice с уже проверенным improved SYSTEM.**
Не запускать снова всю тройку и не подбирать новые модели автоматически.

Для этого есть конкретное основание: diagnostic T1 и T2 на том же SYSTEM дали
полные объяснения discovery/model_tools. T3 оборвался на JSON-примере; это
отдельный известный дефект, а не доказательство отказа любых обычных ответов.
Сначала 1–2 новых core-вопроса на текущем корпусе и **том же общем ledger**.
Если ответ error, обрезан по смыслу либо не подтверждается источниками —
остановить эту попытку; не расширять бюджет и не продолжать подбор вслепую.

Если smoke содержательно пройдёт, оценить реальные Q1–Q6 и необходимые
перефразировки, затем сделать новую живую запись обязательных шагов. Для SPEC
должны действительно работать объяснение устройства/запуска/ограничений,
текущий Git из MCP и честный unknown. Статус `ok` и существующая ссылка не
заменяют оценку полноты и смысла. Обрыв Q6, обычного вопроса об устройстве,
нельзя оправдать ограничением T3.

T3 — просьба сгенерировать вложенный JSON-пример — не является отдельным
обязательным требованием текущей SPEC. Его можно честно сохранить как известное
ограничение модели, если обязательные core-сценарии проходят. Это не разрешает
объявить универсальную точность помощника или замолчать неудачный comparison.
Если обязательные сценарии не проходят, результат остаётся частичным, без
фиктивного PASS и без выдачи удачного отдельного кадра за полную приёмку.

Код, сервер 8071, ключи и общий ledger в этом анализе не менялись. Финальный
выбор, дополнительные живые вызовы и видео выполняет координатор в пределах
уже разрешённого общего бюджета; данный файл их не имитирует.
