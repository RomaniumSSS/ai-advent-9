# Запуск и диагностика

## CLI и браузер

CLI принимает `/help` и вопрос. Браузер обращается к тому же `Assistant.answer`.
По умолчанию интерфейс слушает только 127.0.0.1:8071. `--repo` фиксирует Git-root
на старте. В UI видны абсолютный Git-root, текущая ветка, head и repository_id.

## Облако и бюджет

Реальный режим включается явно `--live --budget-usd <разрешённый лимит>`.
Ключ OPENROUTER_API_KEY читается из окружения или `--env-file /безопасный/путь/.env`.
Файл ключа не входит в индекс, не копируется и не отдаётся в API.
Модель deepseek/deepseek-v4.1-flash через OpenRouter; только точный маршрут
deepinfra/fp8, fallback отключён,
max_retries=0, max_tokens=1600. Один вопрос создаёт не более одного запроса модели.

Бюджет хранится в SQLite ledger, общий для процессов с одинаковым data-dir.
До вызова резервируется потолок по тарифу без скидки: $0.20/M input и $0.60/M output.
Неизвестный usage или неоднозначный сетевой сбой сохраняет резерв, cost=null.
Повтор после ошибки пользователь запускает сам; автоматического retry нет.
Данные по умолчанию лежат в day31/.runtime; их не включают в Git.

## Ошибки и ограничения

Пустая выдача документов означает «нет данных», вызова модели в этом случае нет.
Ошибка MCP, timeout модели, invalid JSON, обрезанный ответ и неизвестные source_ids
дают status=error. Это касается любого неизвестного ID как в source_ids, так и
в inline-ссылках вида [20-символьный hex ID]. Если inline-ID принадлежит реально
найденному фрагменту, но пропущен в source_ids, код добавляет его в массив после
заявленных ID, в порядке появления и без дублей. Text/status не меняются, новой
генерации нет; добавления отмечаются в trace. JSON Schema проверяется до и после
нормализации, ok по-прежнему требует хотя бы одну ссылку. Наличие существующей
ссылки не доказывает смысловую верность.
Документы и MCP-данные считаются недоверенными данными, а не инструкциями модели.

## Команды облачного режима

Только после явного разрешения бюджета. Пример использует переменную
DAY31_BUDGET_USD с согласованным пределом; её значение не устанавливается кодом:

```bash
uv run python -m day31.web --live \
  --env-file /безопасный/путь/.env --budget-usd "$DAY31_BUDGET_USD"
uv run python -m day31.cli '/help Как устроен Git MCP?' --live \
  --env-file /безопасный/путь/.env --budget-usd "$DAY31_BUDGET_USD" --json
```

Перед облачным стартом бесплатный metadata preflight подтверждает активный
endpoint с точным tag deepinfra/fp8, JSON Schema/reasoning и остальные параметры
запроса, а также тариф без скидки не выше резерва. При росте
тарифа или недоступных метаданных запуск прекращается до платного запроса.
Reasoning отключён через enabled=false, require_parameters=true: неподдерживаемые
параметры не должны тихо игнорироваться провайдером.

## Браузерная проверка без облака

```bash
uv run python -m day31.tests.browser_check --output /tmp/day31-browser-check
```

Chromium проверяет настоящий Git/MCP, переход к источнику, unknown, текстовый
render модельного HTML, desktop/tablet/mobile без горизонтального overflow.
Отчёт и снимки складываются в указанный каталог. Это не живая облачная приёмка.

## Новый сценарный прогон и запись

Сервер должен уже работать. Скрипт не принимает ключ и не включает облако сам.
Новый output-каталог обязателен; существующие прогоны не перезаписываются.

```bash
uv run python -m day31.recorder.run_demo --dry-run \
  --output /tmp/day31-new-offline-dry
# После разрешения расходов и запуска сервера с --live:
uv run python -m day31.recorder.run_demo --dry-run --expect-mode live \
  --output /tmp/day31-new-live-dry
uv run python -m day31.recorder.run_demo --record --expect-mode live --hold-seconds 6 \
  --output /tmp/day31-new-live-record
```

Каждый прогон отправляет три новых вопроса через UI, раскрывает источник и
фактический MCP result. Записываются trace_id/usage/время, ответы, скриншоты и
события этого запуска. `--expect-mode offline` по умолчанию не даст незаметно
потратить бюджет на облачном сервере. `--expect-mode live` явно разрешает новые
ответы через уже настроенный сервер с его общим ledger.

Record создаёт новый raw WebM и MP4 через ffmpeg, затем отдельный ffprobe.json.
Офлайн-запись называется Day31-offline.mp4, облачная — Day31-live.mp4.
Успешный сценарий проверяет статусы и новые trace_id, но не подменяет независимую
проверку смысла ответов или просмотр кадров. CLI проверяется отдельно; этот
скрипт записывает только браузерные шаги 1–3 сценария.

Параметр `--hold-seconds` (по умолчанию 6, допустимо 0 < значение ≤ 60) задаёт
отдельную паузу для каждого читаемого экрана ответа/источника, начала MCP-вызова
и его результата.
Эти паузы начинаются после получения настоящего результата; ожидание API остаётся
отдельным. Длинный ответ и источник автоматически прокручиваются экранами с
перекрытием 180 px; каждый экран сохраняется отдельно и удерживается указанное
время. Текст не сокращается и не заменяется. Для более медленного чтения можно
увеличить hold-seconds. В dry-run паузы чтения отключены, даже если
параметр передан. Запрошенное и фактическое значения сохраняются в manifest.

Браузерную проверку можно направить на другой Git-root:

```bash
uv run python -m day31.tests.browser_check --repo /путь/к/repo \
  --output /tmp/day31-browser-other-branch
```

Ожидаемые Git-root, ветка и HEAD получаются независимыми командами `git`, затем
сравниваются с точными UI/API значениями. Detached HEAD учитывается как branch=null;
имя ветки разработчика в проверке не зафиксировано.

В MCP сначала показывается начало настоящего JSON (вызов/discovery), затем
прокручивается внутренний `pre` до `result.branch` и `result.head`. Код сверяет
полный JSON с API и проверяет, что эти строки видны в viewport, не создавая
сокращённую копию результата. Сохраняются `NN-mcp.png` и `NN-mcp-result.png`.
У длинного ответа/источника первый кадр сохраняет прежнее имя `NN-answer.png` /
`NN-source.png`, следующие получают суффиксы `-02`, `-03` и т. д. `events.jsonl`
хранит номера кадров, координаты прокрутки и проверку видимости branch/head;
полный trace и исходный ответ остаются в `NN-answer.json`.

Лексический поиск сохраняет до 24 исходных уникальных терминов и отдельно
добавляет до 16 уникальных технических синонимов. Широкое слово «действие»
расширяется только при техническом контексте вопроса. Общие слова сами по себе
не превращают нетехнический вопрос в вопрос по проекту. Ранжирование остаётся
FTS5/BM25, без привилегий для отдельных файлов, векторов или дополнительной модели.

## Отдельный pilot сравнения моделей

Финальный производственный профиль — DeepSeek V4.1 Flash/DeepInfra; сравнение не выбирает
модель автоматически и не меняет UI. Явные профили находятся в доверенном
`day31/eval/model-profiles-20261016.json`: id, model, exact_route, тарифные потолки
input_usd_per_m/output_usd_per_m, max_output_tokens и reasoning. Адаптер копирует
reasoning в неизменяемый профиль; каждый профиль использует один общий механизм
запроса, предварительного резерва и обработки ошибок.

```bash
uv run python -m day31.eval.compare_models --plan \
  --profiles day31/eval/model-profiles-20261016.json --output /tmp/day31-compare-plan-new
# После независимого ревью, с уже разрешённым общим бюджетом:
uv run python -m day31.eval.compare_models --execute --budget-usd 0.50 \
  --env-file /безопасный/путь/.env \
  --profiles day31/eval/model-profiles-20261016.json --output /tmp/day31-compare-pilot-new
```

По умолчанию выполняется только plan: бесплатные metadata preflight всех трёх
exact endpoints, настоящий retrieval/MCP один раз на каждый из трёх вопросов,
расчёт потолка всех девяти запросов против текущего остатка. Если вся серия не
помещается, ни один запрос модели не отправляется. Ledger прибит к существующему
`day31/.runtime/live-20261016/budget.sqlite3`; runner не создаёт новый ledger и не
обнуляет бюджет. Каждый платный вызов затем использует прежний ledger.reserve.
Если другой процесс потратит остаток между общим расчётом и вызовом, серия
остановится с partial_budget; уже полученные результаты сохранятся.

Три профиля выполняются параллельно в ThreadPoolExecutor(max_workers=3),
вопросы Q6, P1 и T3 внутри каждого профиля идут последовательно. Общие
preflight, снимки и проверка бюджета завершаются до запуска потоков. У профилей
отдельные provider/client и каталоги результатов; итоговую summary собирает
главный поток после их завершения. Источники и Git фиксируются один раз для
вопроса; все кандидаты получают одинаковые сериализованные данные, SYSTEM из
`results/prompt-diagnostic-20261016/tested-system.txt` и одинаковую провайдер-
совместимую wire JSON Schema с полной последующей локальной проверкой. Gold не
читается runner и не передаётся модели. Режимы reasoning и предел вывода берутся
из явных профилей и могут различаться: это сохраняется в каждом результате.

Новый output-каталог хранит summary с общим потолком, preflight и состоянием
бюджета, fingerprint корпуса/SYSTEM/schema/inputs, снимки context, отдельный
файл каждого вызова с фактическим input, финальным JSON, ошибкой разбора,
finish_reason, receipt, trace, временем, usage/cost и счётчиком reasoning_tokens,
если API его вернул. Текст reasoning и ключи не сохраняются. Ошибки не вызывают
повторных запросов; отрицательная оценка смысла остаётся задачей отдельного reviewer.

## Фактические ограничения финального профиля

Production SYSTEM совпадает с проверенным улучшенным prompt из
`results/prompt-diagnostic-20261016/tested-system.txt`. Это не гарантирует
смысловую полноту. У финального DeepSeek в T3 внешний JSON и source ID валидны,
но JSON-пример внутри text — псевдо-JSON и не проходит как настоящий JSON-код.
Исторически GLM4.7 возвращал неполный код или type=func при валидном внешнем JSON
и finish_reason=stop; это не было доказано как исчерпание лимита токенов.
Ссылки проверяются кодом, смысл, полнота и внутренний кодовый пример требуют
отдельной оценки.

[Первый pilot трёх моделей](../results/compare-models-pilot-20261016/summary.json)
завершился 9 API/response-ошибками; качества кандидатов сравнить не удалось.
В [pilot после wire-fix](../results/compare-compatible-pilot-20261016/summary.json)
DeepSeek дал три ответа с валидным внешним JSON. GLM5.3 Q6 завершился по length,
P1/T3 — HTTP429; Qwen — три HTTP404. Недоступные ответы не ранжируются по качеству.
Для сдачи выбран доступный DeepSeek, без автоматической маршрутизации.
[Read-only диагностика](../results/compare-models-pilot-20261016/diagnosis.json)
не установила исходные upstream-причины. Неизвестные расходы не считаются нулём,
сохранённые резервы и лимит ledger не менялись.

Адаптер теперь распознаёт response.error, даже если SDK получил HTTP 200, и
сохраняет только allowlisted upstream code/type/status в диагностике вызова.
Для SDK HTTP-ошибки сохраняется тот же набор и имя класса исключения. Message,
raw body, скрытый reasoning и ключи не сохраняются; upstream-ошибка не выдаётся
за обрыв по token limit. Автоматических повторов нет.

В диагностическом запросе GLM5.3/DeepInfra подтверждён отказ grammar-компилятора
на uniqueItems: `Grammar error: Unimplemented keys: ["uniqueItems"]`.
В wire-схеме убран только `properties.source_ids.uniqueItems` из отдельной копии;
strict=true и остальные ограничения сохранены. Локальная ANSWER_SCHEMA остаётся
полной с uniqueItems=true: дубли source_ids и прочие нарушения отвергаются до
нормализации и после неё. Это совместимость транспорта, без ослабления guards.
Диагностический факт не устанавливает причины всех предыдущих API-ошибок.
