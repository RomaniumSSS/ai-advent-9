# День 9 — сжатие истории

Два режима рядом: полная история и summary со свежими сообщениями.
Модель по умолчанию — **DeepSeek V4 Flash 0731** через OpenRouter.
Код дня 9 самостоятельный; старые дни не изменены.

```bash
uv run day09/web.py --env-file /путь/к/.env
# http://127.0.0.1:8039
```

Ключ задаётся через `OPENROUTER_API_KEY`. Панель и эксперименты используют общий
сохраняемый бюджет $0.50 (`results/budget.db`), закреплённый OpenInference FP8,
без fallback и скрытых повторов SDK. Reasoning отключён. В парных прогонах
температура 0; это не гарантирует одинаковые ответы.
DeepInfra проверен первым, но оказался нестабилен; его частичные результаты
сохранены отдельно и не включаются в основное сравнение.

## Что делает панель

Один вопрос отправляется в две независимые сессии. Слева вся история каждый раз
уходит модели. Справа старая часть заменяется summary; полный архив остаётся
видимым. В раскрываемом блоке можно прочитать summary и результаты сохранённых
сравнений. Счётчики показывают вход/выход API, расход на summary и общий итог.
Локальный размер контекста помечен как оценка.

Сценарии «Планирование проекта» и «Обычная беседа» содержат по 16 фиксированных
вопросов. Кнопка подставляет очередной вопрос, отправка отдельная. Для второго
сценария начать новый эксперимент: после подтверждения очищаются обе истории,
summary и статистика сессий, **но не общий бюджет**.

При частичном успехе повторяется только неудавшаяся сторона. При обрыве HTTP
повтор с тем же ID возвращает сохранённый результат без нового вызова модели.
Незавершённый ID после аварии сервера не запускается автоматически повторно:
нужно проверить историю. Одну сессию следует использовать одним процессом —
согласование нескольких одновременно работающих экземпляров агента не реализовано.

## Механизм и пределы

| Настройка | Значение | Смысл |
| --- | ---: | --- |
| `keep_messages` | 6 | Минимальный свежий хвост: 3 пары вопрос/ответ |
| `batch_messages` | 10 | Сколько старых несжатых сообщений накопить перед сжатием |
| `summary_tokens` | 600 | Максимум готового summary по локальной оценке |
| `max_output_tokens` | 2000 | Потолок генерации summary |
| `AgentConfig.max_tokens` | 4000 | Потолок обычного ответа |
| Ориентир в промпте summary | 120 слов | Мягкая просьба, не технический ограничитель |

Перед 9-м вопросом накоплены 16 сообщений: первые 10 сжимаются, последние 6
остаются дословно. Следующая попытка — перед 14-м вопросом. Это верно для успешных
ходов и принятого первого summary. Между сжатиями хвост растёт: сразу после
ответа на 9-й вопрос в нём уже 8 сообщений. Ошибка сжатия сдвигает момент его
успешного применения; пустой ответ не добавляет сообщений.

Сборка запроса:

```
system → summary (assistant, пометка исторических данных) → свежие пары → вопрос
```

Суммаризатор получает предыдущий summary и новую старую часть. Промпт требует
различать слова пользователя и неподтверждённые предложения ассистента.
Продолжение беседы не считается согласием. Summary не получает системную роль,
но это не абсолютная защита от выполнения инструкций из истории.

SQLite сохраняет summary и число покрытых сообщений одной транзакцией;
только после успешной записи меняется состояние в памяти. Пустой, оборванный,
слишком длинный или не уменьшающий контекст пересказ отклоняется. Ошибка записи
тоже оставляет прежний контекст. Оплаченная попытка входит в расход даже при
отклонении; на следующем ходе можно попробовать сжатие снова.

## Учёт денег и сравнение

`chat` и `summary` — разные виды вызовов в журнале. Отсутствующий usage остаётся
неизвестным. Измеряем вход, выход и их сумму, включая служебные запросы.
Ошибки API без usage перечисляются отдельно: их неизвестные токены не входят
в показанную сумму, а бюджет удерживает резерв неизвестных списаний.
Разные ответы двух режимов дают разную последующую историю: процент отражает
два реальных диалога, а не чистый эффект сжатия идентичного текста.

Перед каждым платным вызовом `experiment.py` атомарно резервирует деньги.
Для этой версии модели проверен ByteLevel BPE без нормализации: резерв входа
считается по UTF-8 байтам текста с запасом 1024 на каждое сообщение и ещё 1024
на весь шаблон; выход — по `max_tokens`. Это консервативный расчёт, не API-замер.
Тариф ограничен `provider.max_price`: $0.05/$0.16 за миллион входа/выхода.
При превышении границы дальнейшие вызовы блокируются. Неизвестное списание
удерживает резерв; завершённые расходы восстанавливаются после перезапуска.

Первоначальный резерв по всему окну оказался чрезмерным для отклонённых
запросов. Старую завершённую часть сверили с независимым дневным счётчиком
ключа. Сверка сохраняется отдельно; индивидуальные usage ошибок не обнуляются.
[Формула и источник токенизатора](results/tokenizer-reserve-evidence.json),
[сверка биллинга](results/billing-reconciliation.json).

## Проверки

```bash
uv run day09/test_compression.py  # 10 групп, включая новый процесс Python
uv run day09/test_budget.py       # резерв, конкуренция, неизвестный расход
uv run day09/test_web.py          # HTTP, повтор ID, восстановление, Origin
uv run day09/test_resume.py       # продолжение неполной пары без дубля
uv run day09/test_reconcile.py    # отставший счётчик и границы сверки
```

Эти проверки используют подставной API и временные базы. `tiktoken` при первом
запуске на чистой машине может скачать словарь; проверенный запуск использовал
локальный кеш. Визуальная проверка с подставной моделью —
[отчёт](demo/visual-check.json): 1280, 768 и 375 пикселей, отправка в обе стороны,
перезагрузка с summary, оба сценария, отсутствие ошибок JavaScript.

Реальные прогоны запускаются отдельно и стоят денег:

```bash
uv run day09/test_live.py --env-file /путь/к/.env --start 1 --repeats 3 --resume
uv run day09/analyze.py
uv run day09/quality.py
```

Для новых измерений выбирается новый диапазон номеров, например `--start 4`.
Завершённые результаты при `--resume` пропускаются; незавершённые продолжаются
только при совпадении промпта и состояния архива. Успешная сторона уже начатого
хода не вызывается повторно. При обрезанном ответе или сбое сохранения
автоматическое продолжение запрещено: нужен разбор состояния. Временные 429/502/503/504 допускают два явных повтора
с паузой 15 секунд и отдельным учётом. Частичные и диагностические результаты
не заменяются успешными. `results/final/project-r1.json` … `project-r3.json` и
`personal-r1.json` … `personal-r3.json` — три итоговых повтора каждого
сценария; прежний промпт с ориентиром 200 слов и его результаты сохранены
в `results/openinference/`. Там выявлены слишком длинные summary и перенос
неподтверждённых предложений в ограничения, поэтому промпт был уточнён.

`quality.py` проверяет наличие заранее заданных фактов и отменённого значения
в финальном ответе. Это лексическая проверка, не семантический судья: отрицания,
усиленные ограничения и выдуманные решения требуют отдельного чтения ответов.

## Полученный результат

Все шесть пар завершены, в каждой два успешных сжатия. По сумме полученных
usage: 556 078 → 411 039 токенов (−26,1%), известная цена −7,3%.
В одной паре токенов стало на 18,1% больше: длинные ответы и стоимость
пересказов не окупились. Экономия не гарантирована для каждого разговора.

Семантическая оценка контрольных фактов ассистентом: полная история 78/87,
со сжатием 81/87; оба режима теряют детали и добавляют неподтверждённые условия.
Человеческая приёмка отдельно. [Полный отчёт с таблицами](VERIFICATION.md),
[видео кода и реальной панели](demo/README.md) — около 62 секунд без звука (×1,25).
Все пределы, проверки механизма и фактические ошибки записаны в отчёте.
