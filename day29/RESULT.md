# Day29 — результат локальной оптимизации

10.10.2026, Mac M2 / 16 GiB, macOS 15.6.1, Ollama 0.33.3, Python 3.14.
Рабочая ветка `day29-local-optimization`, база `ca90584`. Код и живая запись
готовы локально; окончательное независимое ревью указано в
[implementation-validation.md](results/implementation-validation.md).
Пользовательская приёмка и публикация ещё не выполнены.

Оптимизация доказана **по полноте сложного ответа на проверенном наборе**.
Ускорение не получено. Более полный ответ требует больше времени.

## Что изменилось

Самостоятельный RAG-справочник использует тот же read-only индекс Day25,
эмбеддер `qwen3-embedding:0.6b` и генератор `qwen3:8b` Q4_K_M, что Day28.
Индекс не пересчитан; generation `5d5502c69976163325ad6c35`, DB SHA-256
`9894d937c4bcbae653459a6fe758f231992571e436622a0cd33fcda7f707f11b`.
Runtime обращается только к локальной Ollama. Day01–28 не изменены.

| Настройка | B: исходный Day28 | F: выбранный кандидат |
| --- | --- | --- |
| temperature | 0 | 0 |
| context window / num_ctx | 8192 | 6144 |
| max output / num_predict | 1024 | 384 |
| think | false | false |
| Prompt | 3–4 кратких предложения | Полные требования каждого объекта, затем различия; факты строго по контексту |
| Квантование | Q4_K_M | Q4_K_M |

Однофакторные T/M/C/P и один составной F проверены до финальной серии.
Температура 0.2, отдельное снижение вывода и окна не исправили полноту E02;
изменение prompt исправило её. Финальный F оставляет temperature=0 и использует
меньшее окно/лимит, достаточные для неизменённого входа и проверенных ответов.
[Пробные ответы и ограничения](results/pilot-assessment.json),
[решение о кандидате](results/candidate-pilot-assessment.json).
Это не обучение весов и не основание ожидать улучшение на любой задаче.

## Сравнение до и после

Свежие B/F: три заранее известных вопроса × два warm повтора на профиль.
Четыре отдельных прогрева исключены; порядок блоков B/F, затем F/B.
Вопрос, тексты источников и их порядок одинаковы; профили зафиксированы до серии.
Время ниже — генерация на замороженном RAG-контексте; в видео выполняется
полный новый RAG, включая embedding и retrieval.

| Проверка | B | F |
| --- | --- | --- |
| E01: требования Day18 | Все 6 групп фактов, оба повтора | Все 6 групп фактов, оба повтора |
| E02: сравнение Day19/20 | 2/5 групп полностью, 3 частично | 5/5 групп полностью, оба повтора |
| E03: отсутствующий бюджет | unknown, без суммы/источников | unknown, без суммы/источников |
| E02 generation median | 43.513 s | 100.058 s |
| Общая generation median, 6 запросов | 29.781 s | 37.127 s |
| Median наблюдённого максимума summed RSS | 5.959 GiB | 5.498 GiB |
| Cold E02, одна попытка | 42.946 s | 81.196 s |

E02 стал примерно **в 2.30 раза медленнее**, общая медиана — на 24.7% больше.
RSS ниже на 7.75%: это меньше заранее выбранного порога 10%, поэтому отдельный
выигрыш по ресурсу не заявляется. Критерий оптимизации выполнен только за счёт
полноты E02 без регрессии E01/E03 и ошибок источников.

Все шесть пар повторных ответов совпали точно, включая JSON модели.
Это наблюдение на маленькой выборке из двух повторов и трёх известных вопросов;
независимого holdout и статистической оценки нет. Поддержку фактов и полноту
проверяли агенты по исходным заданиям; валидные ссылки сами по себе её не доказывают.
[Семантическая оценка всех 12 ответов](results/warm-semantic-assessment.json),
[вычисленный verdict](results/optimization-verdict.json),
[отдельные значения, диапазоны и медианы](results/public-summary.json).

RSS — максимум наблюдавшейся каждые 0.5 s суммы daemon + native llama-server;
в финальной warm серии полный набор процессов стабилен. Это не полный пик
Apple Metal/unified memory: короткие пики могут быть пропущены, общие страницы
могут учитываться дважды. `/api/ps` allocation/placement записаны отдельно.
Swap относится ко всей машине. Cold подтверждает выгрузку из Ollama,
но не очистку файлового кеша ОС; один cold повтор не оценивает распределение.
Начальные pilot RSS и времена не подходят для доказательства выигрыша: старый
sampler пропустил native runner, а режимы загрузки смешивались. Ошибки сохранены.

## Проба Q8

Скачана официальная `qwen3:8b-q8_0`: та же архитектура, 8.2B параметров и chat
template; меняется квантование весов. Файл модели примерно 8.9 GB на SSD.
Тот же F, вопрос и контекст, temperature=0, ctx=6144, max output=384.

Реальная попытка заняла 140.812 s с загрузкой и закончилась
`done_reason=length`: 384 токена, незавершённый JSON. Наблюдённый максимум RSS
8.571 GiB. По заранее указанному stop condition серия остановлена: два плановых
warm повтора **не запускались**. Это попытка квантования, а не завершённое
парное сравнение качества/скорости. Она не доказывает, что Q8 вообще хуже Q4.
Старый controller не сохранил preparation/series metadata при ошибке первого
прогрева; эти сведения не восстановлены задним числом. Durability исправлена
и проверена офлайн для следующих запусков.

Для задачи оставлена Q4: проверенный полный ответ помещается в выбранный лимит.
Q8 выгружена из RAM; скачанные файлы сохранены на SSD, прежние модели не удалены.
[Оценка Q8](results/quantization-assessment.json),
[проверка происхождения](results/quantization-preflight.json).

## Проверки и поставка

- 45 офлайн тестов GREEN, включая реальные RED→GREEN для guards, сопоставимости,
  RSS, run grouping и сохранения ошибочного первого Q8 прогрева. Это тесты
  обвязки, отдельные от реальной оценки модели.
- Браузерные фикстуры desktop/tablet/mobile и HTTP PASS; ноль page errors.
  Эти проверки используют явно обозначенный mock engine и не измеряют LLM.
- 25 генераций в экспериментах: 6 pilot, 16 warm с прогревами, 2 cold, 1 Q8.
  Затем два dry run и два дубля записи: ещё 16 новых live запросов. Всего
  41 генерация, из них одна неудачная Q8. Первый дубль сохранён с пропуском
  численного swap; новый record-02 исправляет показ данных.
- [Живое видео](video/Day29-live.mp4): 328.48 s, H.264, 1280×1000, 25 fps.
  Четыре новых request ID, без ускорения и монтажа; ответы и источники сверены
  с серверными receipts. Полный decode и просмотр девяти кадров самого MP4 PASS.
  [Подтверждение](results/video-verification.json),
  [публичный журнал записи](results/live-recording.json).
- Фактические роли: Astra high — SPEC/PLAN; Sol high — код/тесты;
  Luna medium — первое ревью; Astra xhigh — обязательное второе и итоговый аудит.
  Координатор выполнил эксперименты, запись и итоговую сборку. Usage/cost не выданы.

Версия evaluator при замерах (`fbe696ad…`) сохранена отдельно. После них
исправлены только guards/postprocessing/controller durability (`fdd23fa6…`),
без изменения core/sampler/payload. Выбор `selected=candidate` меняет начальное
значение UI; настройки измеренного F неизменны. Provenance:
