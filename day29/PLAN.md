## 1. Минимальная реализация

- `core.py`: самостоятельные read-only индекс/retrieval/loopback-клиент, профиль,
  сборка контекста, source_refs и статусы done/unknown/error. При переносе основы
  Day28 сохранить причины его двух `AICODE-NOTE`: byte-bound включает schema/template
  reserve; фильтр явных public-дней защищает от соседних заданий и ложных отказов.
  Никаких imports `day28` или запусков его runtime из Day29.
- `profiles.json` и `eval-suite.json`: декларативные настройки/варианты prompt и
  три вопроса с исходной семантической рубрикой Day28. `baseline` неизменяем для
  сравнения; пользовательский выбранный профиль записывается только после оценки.
- `evaluate.py`: preflight, freeze-contexts, ограниченные pilots, сравнение,
  JSON receipts, сводка и проверка сопоставимости. Отдельный CLI вопроса допускается
  в том же модуле. Python stdlib и текущий инструмент запуска; без новых зависимостей
  ради framework/pytest. Небольшой sampler памяти можно выделить в `metrics.py`.
- `app.py`/`static/`: loopback `127.0.0.1:8069`, вопрос, выбор baseline/кандидат,
  полный ответ, источники, параметры и метрики; таблица сохранённого сравнения
  явно помечена прошлым run. Кнопки запускают новые реальные запросы.
- `tests/`, `results/`, `video/`; полные receipts/контексты только в игнорируемой
  `private/`, публикуемый отчёт содержит разрешённые assignment-примеры и агрегаты.
  `actions.jsonl` — только существенные этапы/ошибки/решения и ссылки на evidence.

## 3. Ограниченный эксперимент

Сначала свежий baseline E02 и четыре однофакторных pilot E02; затем максимум один
составной pilot. Это подбор на известных кейсах, не независимая оценка обобщения.

| Профиль | Отличие от baseline | Гипотеза |
| --- | --- | --- |
| B | temp 0 / ctx 8192 / predict 1024 / исходный SYSTEM | Точка отсчёта |
| T | temperature 0.2 | Проверить влияние вариативности на полноту |
| M | num_predict 384 | Проверить достаточность и ограничить худший расход вывода |
| C | num_ctx 6144 | Уменьшить резерв контекста без изменения входа |
| P | SYSTEM: краткий список требований по каждому объекту и затем различия | Убрать потерю аспектов в 3–4 предложениях |
| F | Только пригодные изменения предыдущих pilots | Проверить их взаимодействие |

Уменьшение max tokens само по себе не ускоряет ответы, уже заканчивавшиеся раньше;
уменьшение context window не обязано уменьшать фактическое потребление памяти.
Оба результата проверяются, не обещаются. Если ctx6144 не вмещает целый вход,
оставить 8192 и сохранить причину; не добавлять sweep в поиске удобного окна.
Для финального сравнения выбрать F либо один из T/M/C/P по рубрике и заморозить
конфигурацию/hash до повторов; выбор/отказ от каждой настройки объяснить.

Финальные warm-повторы: для каждого кейса 2 независимых запроса без chat history
на B и F. Порядок кейсов E01→E02→E03 одинаковый в каждой серии; порядок блоков
профилей B/F, F/B для двух повторов. При каждом переходе профиля загрузить
его с точными options и выполнить один исключённый из оценки прогрев; прогрев
сохранить отдельным receipt. Это **12 оценочных warm запросов**, до 6 pilots,
2 cold E02 и до 4 финальных прогревов (до 24 вызовов генератора без quant/video).
Если final совпадает с B, не объявлять B новым улучшением.

Cold: получить общий lock, убедиться в отсутствии чужого inference, выгрузить
только нужный генератор, подтвердить отсутствие в `/api/ps`, выполнить один E02
на B и один на F. Cold означает выгрузку модели из Ollama, не очистку дискового
кеша ОС. Если это нельзя подтвердить — cold остаётся NOT MEASURED с причиной;
не перезапускать общий Ollama и не выдавать такой запуск за cold.
Warm: перед каждым блоком зафиксирован завершённый прогрев данного профиля и
присутствие модели в `/api/ps`; неожиданный reload означает несопоставимость
блока, а не обычный warm. Температурные результаты не обещают детерминизм. Выборка из двух повторов
мала: это наблюдаемая повторяемость на трёх кейсах, не оценка статистической устойчивости.

Генерация, embedding и выгрузка последовательны под глобальной per-user блокировкой;
дополнительно брать существующий lock Day28
`tempfile.gettempdir()/day28-local-rag-{uid}.lock`, чтобы не мешать старому приложению.
Одинаковый порядок захвата lock во всех входных точках. Внешние программы, не
соблюдающие lock, автоматически не контролируются; мешающий запуск обозначить
в receipt, не убивать чужой процесс. До каждого блока сохранить список моделей,
RAM/swap, время и параметры. После технической ошибки без retry сохранить исход;
один повтор разрешён только после новой диагностированной причины, отдельным ID.

Квантование — отдельная ограниченная ветка: подтвердить официальный тег второго
квантования той же Qwen3 8B, происхождение/architecture/parameter count, размер,
свободный диск и пригодность для 16 ГБ. При подготовке подтверждён официальный тег `qwen3:8b-q8_0`, manifest digest
`e56358ca25dd14db6853a9f68a92d717aaa6f0a94250a72d1a0f3d86a9f30130`,
размер загрузки 8 851 089 053 байта; evidence —
`results/qwen3-8b-q8_0-registry-manifest.json`. Root начал подготовительную загрузку
и сохраняет её исход в `results/quantization-download.json`; факт окончания
и достаточность памяти для inference ещё проверить. До загрузки: около 28 GiB
свободного диска, RAM 16 GiB, swap used около 3005.5 MiB. Загрузка весов допускает
сеть только на этапе подготовки; runtime запросы идут только в loopback.
Если выполнимо, максимум один warmup и 2 E02 warm повтора на второй квантизации,
тот же prompt/options/context; Q4 данные берутся из сопоставимой финальной серии.
При достаточных условиях quant-проба добавляет максимум 3 вызова (1 прогрев + 2 E02),

При выраженной нехватке памяти остановить эксперимент и сохранить причину.
Не обещать Q8 превосходство, размещение полностью в памяти или выигрыш скорости.
Quant-проба не заменяет сравнения B/F и не считается тестом всей suite.

## 4. Метрики и правило вывода

В receipt: run/request/case/profile/repeat IDs, phase/mode, timestamps,
model/digest/quantization/options, context/prompt hashes, index identity,
raw JSON и материализованный ответ, source validity, done_reason/error,
Ollama counts/durations и wall-clock. `done_reason=length` — ошибка завершения.
Tok/s = eval_count / eval_duration только при положительной длительности.
Общий RAG total замеряется в живом приложении; generator replay исключает
embedding/retrieval и подписан отдельно. Нельзя складывать median разных фаз
и выдавать её за измеренный median полного запроса.

Sampler до/во время/после запроса: timestamp/PID/process identity/RSS для daemon
и runner-процессов Ollama (например, каждые 200 мс); сохранить интервал и пропуски.
Показать observed max/sum RSS как максимум наблюдённых значений, не точный peak:
короткий пик мог быть пропущен, shared pages могут учитываться несколько раз,
Metal/unified memory не полностью описывается RSS. System swap used до/после
и доступные pageout/swap counters — показатели всей машины, не только LLM.
`/api/ps` model size/processor placement — отдельные runtime metadata.
Не удалось наблюдать процесс/метрику — `null`, причина и ограничения сравнения.

На каждый ответ отдельно: JSON/source validity, supported facts, coverage каждого
пункта рубрики, unknown, ошибки. Оценку смысла оформить таблицей с выдержками
разрешённых assignment-ответов; не подменять её наличием слов или source refs.
Показать individual values, median и min/max для каждого кейса/профиля; агрегат
скорости — median всех 6 warm generation wall times на профиль. Для ресурса —
median наблюдённых максимумов одного и того же набора процессов по 6 запросам,
только при одинаковой схеме наблюдения и размещении; иначе ресурс несопоставим.
Порог 10% — практическое правило выбора на этом наборе, не статистическая значимость.
Не смешивать технические errors с успешными быстрыми ответами; отбракованные
серии остаются видимыми, завершённость обязательной оценки не приписывается.
