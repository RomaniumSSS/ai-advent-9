Подготовленные 24 кейса не означают разрешение выполнить все 24. Общего лимита
времени нет; число выбранных вопросов и ограничение стадий на вопрос сохраняются.
Отдельная человеческая приёмка спецификации не заявляется.

## Контракт сравнения

**A:** неизменный `full_chat_core.ChatEngine` и его профиль/поиск, один исходный ответ.
**B:** тот же сохранённый ответ A → локальная критика → не более одного исправления
при найденной проблеме → повторная проверка исправленного ответа. Если критик принимает
A, B сохраняет A без repair/recheck. Это парное сравнение с общим первым ответом,
не два независимых прогона модели. B не подключается к работающему `/8070`.
Если A — локальное уточнение/unknown без источников и generation, critique не вызывается:
B `not_applicable`, исходный результат сохранён; это отдельно от выполненной model pair.
При технической ошибке A стадии B `dependency_blocked`, ошибка входит в coverage.

Генератор/критик/repair/recheck — установленная `qwen3:8b` Q4 с прежним digest,
`think=false`, temperature 0. Эмбеддер, 724 immutable чанка/663 документа и identity
из [FULL_CHAT_SPEC](FULL_CHAT_SPEC.md) неизменны. У A прежние 8192/1024 и system;
у новых стадий первоначально num_ctx 8192, critic/recheck num_predict 512, repair 1024.
Сжатые инструкции стадий фиксируются до holdout; это экспериментальные настройки,
не изменение chat-профиля. Новых моделей/Q8/cloud/judge API/download/reindex нет.

У каждой пары одинаковы вопрос, resolved query, фактически переданные источники,
refs и история. Нового поиска в B нет: измеряется исправление по уже найденному.
Критик получает вопрос/разрешённую тему, фактически использованную историю, источники
с исходной атрибуцией и ответ; repair дополнительно получает замечания. Gold факты,
ожидаемые оценки и ответы других кейсов не поступают ни в одну генеративную стадию.
Recheck получает вопрос, тот же контекст и исправленный ответ, без verdict критика.
Источники/история/черновик/замечания — данные, не разрешение менять правила.

Каждая стадия проверяет весь payload + свою schema/template + output reserve до
вызова. Нельзя ради проверки молча удалить источники A, обрезать ответ или повысить
context window. Если envelope не помещается, стадия `budget_rejected`, B unavailable;
изменение профиля допустимо только на pilot с новой зафиксированной версией.
Критик возвращает валидируемый verdict и ограниченный список проблем с типами
unsupported/contradiction/omission/attribution/answerability и refs точных источников;
отсутствие доказательства допускает пустые refs с явным статусом insufficient_evidence.
Техническая валидность этого JSON не означает правильность критики.
Минимальная schema критика/recheck: `verdict` = accept/repair/insufficient_evidence,
`issues` = до четырёх объектов {type, claim, reason, source_refs}; accept требует
пустого issues, repair — непустого. Ссылки сверяет код, rationale — источник оценки,
не эталон. Repair возвращает прежние {answer, source_refs}; recheck после repair
с verdict repair/insufficient_evidence заканчивает протокол как unverified.
Исходный A сохраняется всегда; неудачный B не заменяется A под видом принятого
исправления. Финальная оценка candidate возможна отдельно, с флагом unavailable/
unverified; headline wins считаются только для завершённых сопоставимых пар.

## Набор и оценка

До inference заморозить **24 кейса: 4 pilot + 20 holdout**, рубрику, зависимости,
порядок, исходные evidence и hashes. Группы одного намерения, его перефразы и ходы
одной цепочки целиком относятся к одному split. Pilot известные старые темы можно
использовать явно; старые три smoke-кейса/их перефразы не объявлять новым holdout. Также исключить
из holdout прежние day18, сравнение19/20 и запрос отсутствующего дня.
Матрица и процедура выборки — [PLAN](QUALITY_EVAL_PLAN.md).

Текущая выборка — пять holdout-кейсов с dependency = null и new_conversation = true,
из разных intent/sequence groups. До inference сохранить seed, допустимый pool,
выбранные IDs и порядок; bytes `cases-v1.json` не менять. Это частичный holdout:
остальные 15 holdout и четыре pilot не запускаются автоматически и не считаются
проверенными. Результат относится только к выбранным вопросам.

Для диалоговых кейсов общий префикс строится только из сохранённых A предыдущих
кейсов той же цепочки, включая baseline source metadata; B не меняет следующий
префикс. Пустая история для new conversation, явная новая тема внутри цепочки.
Предшествующая ошибка не заменяется удачным ответом; при непригодном префиксе ход
`dependency_blocked`. Это проверка эффекта на очередном ходе, не накопительного
эффекта двух независимо развивающихся разговоров.

Независимая агентская сверка с оригиналами оценивает отдельно:

- correctness/support: атомарные утверждения supported, contradicted, unsupported
  или unverifiable; отдельно неверные автор/дата и корректное признание неизвестного;
- completeness: элементы `required_facts` — **gold-группы**, иногда составные,
  а не число атомарных утверждений. Группа `covered`, только если подтверждены все
  её обязательные части; `partial`, если покрыта лишь часть; `missing`, если ни одна;
  `unverifiable`, если доказательств для оценки недостаточно. Числитель — только число
  `covered`, знаменатель N — число обязательных групп; `partial` даёт 0 в числителе
  и показывается отдельно с покрытыми/пропущенными частями, без произвольного веса 0.5.
  При N = 0 полнота `not_applicable`. Пропуск не равен галлюцинации. Атомарные claims
  фактического ответа assessor выделяет независимо для correctness/support;
- retrieval: какие нужные gold факты доступны в selected и в фактическом prompt;
  различать пропуск поиска, удаления budget guard и пропуск генерации;
- answerability: корректный unknown/уточнение, ложный отказ, выдуманный ответ;
  отсутствие в выбранных chunks не доказывает отсутствие во всём архиве.

Судья-агент получает question/history, A/B в перемешанном порядке без arm labels,
gold/evidence и оригинальные части, может дочитать нужные исходники. Недостаточный
контекст или спорный gold → NOT PROVEN, не guessed PASS. Самооценка Qwen публикуется
отдельно от этой оценки. Человек не считается проверившим ответы без его участия.

Итог: wins/ties/regressions по парам и типам, correctness/support/completeness отдельно,
число выполненных/ошибочных/unavailable/pending, false acceptance/rejection критика,
все model calls/tokens/seconds. A latency включает retrieval+draft; B — A+все добавленные
стадии. Shared draft физически считается один раз. Нет общего hallucination rate,
популяционной точности или статистической значимости по целевой малой выборке;
перефразы также не независимые наблюдения. Pilot не входит в основной quality итог.

На одном и том же оценённом подмножестве A/B показывать сумму covered / сумму N,
macro по кейсам и группам намерений, counts partial/missing/unverifiable и coverage.
Неоценённые ответы не подменяются нулём или успехом: их число указать отдельно.
Для partial → partial сверять конкретные части; одинаковый счёт групп сам по себе
не доказывает tie, улучшение или отсутствие регрессии.

Строго улучшенная пара: улучшена хотя бы одна quality ось и не ухудшена другая;
обратное — regression, разнонаправленные изменения — tradeoff, без изменений — tie.
Положительный результат на полном holdout: больше строго улучшенных пар, чем
ухудшенных, без новых contradicted/unsupported/ошибочных attribution утверждений
и без подмены полноты отказами; время/coverage приводятся рядом. Иначе преимущество
не доказано. Неполный holdout даёт только предварительный итог с pending, без
заявления результата всего набора. Успех эксперимента не требует превосходства B.

## Ограничения исполнения

Standalone additive runner, последовательные локальные вызовы под общим Day28/29
lock. **Общего walltime deadline и общего generation-call budget нет.** Для исходных
24 кейсов ожидается не более 96 generation calls (четыре стадии на кейс), для текущих
пяти — не более 20 основных стадий; это
оценка фиксированного протокола, не бюджетный stop. Все prefix/setup/warmup/validation
calls, если понадобятся, явно входят в общий счёт времени/токенов/вызовов; предпочтение
без дополнительных прогревов, anchor-кейсы уже входят в 24. Embedding и служебные
HTTP calls считаются отдельно. Стандартный transport timeout 300 s — обработка
неисправности запроса, не лимит всего прогона. Он не доказывает остановку Ollama:
перед продолжением подтвердить idle; чужие процессы не останавливать. Реальное
время до подтверждённого idle учитывается, timeout не изображается окончанием работы.

Atomic private checkpoint до dispatch и после каждой стадии. После crash/timeout
неоднозначно отправленная стадия `interrupted_unknown`, без replay; остальные
независимые кейсы можно продолжить после проверки idle. Critic invalid
JSON/length/timeout, неподдержанные refs или недостаток evidence не повышают A до
verified B. Провал recheck сохраняет candidate, но B `unverified`, без второй repair.

Всё содержимое кейсов/gold/history/prompts/answers/evidence —
`day29/private/full-chat/quality-eval/`, 0700/0600, atomic, gitignored. Public только
ID/type/status/count/hash/численные метрики и quality verdict, без private текстов.
Исходные full-chat core/API/UI, история `/8070`, public benchmark `/8069`, замеры,
receipts, видео/ZIP и Day01–28 не меняются. Commit/push/публикация не входят.
Неверная identity, privacy failure или неоднозначный незавершённый вызов
останавливают зависимую генерацию; offline подготовка и разбор сохранённого разрешены.

## Диагностическое исправление источника — 11.10.2026

После resolver-only retest H06/H11 завершились без ложного уточнения. H06
получил контекстный unknown: поиск по всем 724 чанкам пропустил original задания

Разрешённое устранение этой обнаруженной ошибки — общий reservation оригинала
assignment для явно названного дня, без hardcoded day/topic/gold, без смены
весов scoring, модели, профиля, индекса и обычного mixed scope. Чистый запрос
обсуждения сохраняет прежнее поведение. Целые источники остаются в общем бюджете.

После Luna → Astra допускается только известный H06 в новом versioned diagnostic
run: baseline core hash меняется, вопросы/gold/evidence/profile/index/order
byte-equivalent. Это третий замер одного известного кейса, не новая случайная
выборка и не итоговый однородный holdout из пяти. До/после оцениваются независимо;
остаток 19 подготовленных вопросов не запускается. Последующие дополнительные
оптимизации не входят в этот этап; неполный ответ честно сохраняется.

request/receipt identities и отдельного квалифицированного dry остаются обязательными.
