# Как работают Day28 и Day29

Разбор готовой реализации для чтения после возвращения к компьютеру.
Это объяснение устройства, а не отметка о том, что материал уже усвоен.

## Day28: как модель отвечает по нашему архиву

Представь вопрос: «Что требуется сделать в задании дня 18?».

1. Приложение отправляет вопрос локальному **эмбеддеру** — маленькой модели
   `qwen3-embedding:0.6b`. Она превращает смысл вопроса в числовой вектор.
2. Приложение ищет похожие векторы в **готовом индексе Day25**. Индекс хранит
   фрагменты документов и их векторы: его уже построили раньше, заново не строим.
3. Найденные фрагменты вместе с вопросом и правилами ответа отправляются
   локальному **генератору** `qwen3:8b` через Ollama.
4. Qwen пишет ответ и выбирает обозначения источников `S1`, `S2`.
5. Приложение проверяет эти обозначения и показывает исходные тексты из индекса.

Так устроен RAG: **вопрос → поиск фрагментов → ответ по найденному**.
В Day28 поиск и обе модели работают на Mac. Векторный индекс и память диалога
решают разные задачи: индекс помогает найти документы, история хранит разговор.
Индекс не обучает Qwen и не загружает весь архив в её RAM на каждый вопрос.
В публичной демонстрации доступны только документы с условиями заданий.

Источники в ответе помогают проверить сказанное. Их правильные ID ещё не
гарантируют, что модель перечислила все требования или точно передала смысл.
Поэтому Day28 работал технически, но сравнение Day19/20 было неполным.
Отсутствующий точный бюджет нельзя вывести из похожего документа: здесь нужен
ответ «Не знаю по переданному контексту».

## Day29: что именно оптимизировали

Использовали ту же Qwen, тот же индекс и те же найденные тексты. Меняли условия,
в которых модель составляет ответ. Это позволяет связать разницу с настройками.

| Рычаг | Что означает | Что сделали |
| --- | --- | --- |
| temperature | Степень случайности при выборе следующего токена | Проверили 0.2; оставили 0 для справочника |
| max output / num_predict | Максимум новых токенов ответа | 1024 → 384: лимит, не требование обязательно написать столько |
| context window / num_ctx | Окно для правил, вопроса, источников и генерации | 8192 → 6144; вход не обрезали, сначала проверили бюджет |
| Prompt | Инструкция о том, как отвечать | Вместо краткого пересказа потребовали полные требования каждого задания, затем различия |
| Квантование | Точность хранения чисел в весах модели | Попробовали Q8 вместо Q4 у той же Qwen3 8B |

Токен — часть текста, иногда целое слово, иногда несколько букв; число токенов
не равно числу символов. Уменьшение max output само по себе не улучшает факты.
Слишком маленький лимит обрывает ответ — именно это произошло в пробе Q8.

Главное изменение здесь — **prompt**. Краткий исходный ответ описывал общие
различия MCP-инструментов и серверов. Новый перечисляет инструменты Day19,
их цепочку/проверки/результат, а затем регистрацию серверов, выбор и маршрутизацию
инструментов Day20, проверки порядка вызовов и формат сдачи.

На двух warm повторах: исходный профиль полностью покрывал 2 из 5 групп,
кандидат — все 5. Обычный вопрос Day18 и неизвестный бюджет не ухудшились.
Но сложный ответ стал длиннее: медиана генерации выросла **43.51 → 100.06 s**.
Здесь «оптимизировано» означает лучший ответ для справочника с измеренной ценой
в скорости. Настройки для быстрого короткого чата могли бы оказаться другими.

**8B** — примерно восемь миллиардов параметров. **Q8** — квантование весов
примерно до восьми бит. Это разные характеристики. Мы не меняли Qwen3 8B на
другую 9B модель: сравнивали Q4_K_M и Q8_0 той же архитектуры.
Q8 загрузилась и начала отвечать, но выдала незавершённый JSON за 140.81 s
при лимите 384 токена. Плановые warm повторы остановлены. Это не доказывает,
что Q8 хуже вообще; для нашего проверенного режима оставили Q4.
Q8 выгружена из RAM, файл модели сохранён на SSD.

## Как это разрабатывали и проверяли

**SDD**: до кода записали в [SPEC](SPEC.md), какой результат нужен и как его
проверить, а в [PLAN](PLAN.md) — порядок экспериментов. Например, заранее решили
сравнивать одинаковые вопросы/источники и не объявлять улучшение только по
правильному JSON. Отдельного формального согласования текста не было: ты поручил
продолжить реализацию автономно и объяснить после.

**TDD**: сначала тест показывал конкретное неверное поведение, затем его
исправляли и получали GREEN. Например, summary ошибочно объединял разные
эксперименты; новый тест воспроизвёл это, код стал группировать их по run ID.
45 таких тестов проверяют программу. Их моки не могут доказать качество Qwen.

**Живые проверки**: действительно запускали локальные модели, сохраняли ответы
и время, читали требования в исходных документах. Warm сравнивает уже загруженную
модель после проверенного прогрева; cold включает загрузку после выгрузки.
На видео новый запрос дополнительно выполняет embedding и поиск, поэтому его
время может отличаться от генерации на заранее сохранённых фрагментах.

Astra подготовила план, Sol реализовал код, Luna провела первое ревью, Astra
повторно проверила исправления и фактические результаты. Роли выбирались реальными
параметрами инструмента. Это не несколько локальных Qwen, одновременно занявших RAM:
локальные генерации выполнялись последовательно.

Практический разбор у компьютера: открыть `http://127.0.0.1:8069`, посмотреть
две настройки рядом, задать сравнение 19/20 сначала B, затем F, прочитать источники
и сопоставить пропущенные пункты. После — вопрос о бюджете. Все ответы новые,
поэтому запуск займёт время. Сохранённые выводы и границы оценки — [RESULT](RESULT.md).

Параметры Ollama: [Modelfile](https://docs.ollama.com/modelfile),
генерация/think/format: [Chat API](https://docs.ollama.com/api/chat).
