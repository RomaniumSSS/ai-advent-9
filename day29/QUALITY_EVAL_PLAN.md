# Quality eval — план и выборка

Основание: [SPEC](QUALITY_EVAL_SPEC.md). Отдельные `quality_eval.py` и tests;
существующий полный чат использовать как неизменный baseline, не переписывать.
Подготовлен private `private/full-chat/quality-eval/cases-v1.json`: 24 кейса,
14 связанных intent/sequence groups (10 holdout), 17 исходных чанков, 50 gold-групп;
точные цитаты/offsets и смысл независимо сверены с immutable originals: см.
`quality-results/source-audit-summary.json` и private `source-audit-details.md`. Никакого
retrieval inference/embedding/generation при подготовке не выполнялось.

## Подготовка выборки

Read-only инвентаризация подтверждает 24 assignment/694 discussion/6 personal_note
чанков; последние шесть относятся к **одному** документу. В discussion нет буквальных
`чанк`/`chunk`; вопросы о размерах чанков нельзя выдавать за подтверждённое обсуждение.
Темы выбирать после чтения реально существующего оригинала и attribution offsets.

| Основной тип | Кейсов | Обязательное разнообразие |
| --- | ---: | --- |
| Фактический | 4 | assignment и discussion, прямой и косвенный вопрос |
| Несколько источников | 3 | синтез, смешанные source types, детали из разных частей |
| Сравнение | 3 | различия, сходство, ограничения; без выдуманной второй позиции |
| Авторство | 3 | конкретный участник, несколько участников, неизвестная атрибуция |
| Личная заметка | 3 | разные подтверждённые аспекты; общая документальная зависимость |
| Диалог | 5 | два follow-up, короткое продолжение, новая тема, неоднозначный referent |
| Unknown | 3 | отсутствующая деталь, неподтверждённая предпосылка, нехватка сведений |

Итого 24. Теги могут пересекаться, primary type один. Включить минимум три пары
перефраз одного намерения (прямой/разговорный/косвенный), сохраняя их в одном split;
получится не более 21 независимого intent group. Номера дней сами по себе не тема.
Pilot 4 — прежние day18, сравнение19/20, ручные ветки, embedding-note — покрывает
factual, comparison, attribution и personal_note; holdout 20
охватывает все типы. Все цепочки holdout целиком holdout; anchor — другой включённый
кейс, поэтому отдельные «бесплатные» setup generations не появляются. Нужные категории
с реальными пробелами формулировать как unknown/уточнение, не создавать gold из воздуха.

На case сохранить: ID/group/split/type, question, dependency/reset, обязательные
gold-группы с document/chunk/source-member IDs и точными original spans/hashes,
допустимый unknown/неизвестное авторство, запрещённые домыслы, правила полноты.
Для negative case сохранить границу проверенного поиска и недостающий факт;
не обещать абсолютное отсутствие за пределами снимка. Противоречия между источниками
включать только найденные, не требовать их существования. Root сверяет gold до freeze.

Private manifest включает hashes cases/gold/protocol/baseline source/profile/index,
split/order и prepare-only состояние. Freeze вопросов/gold до первого pilot; после pilot менять
можно только протокол B, сохраняя версию. Holdout вопросы не подстраиваются под ответы.
Если corpus/gold defect всё же обнаружен, кейс invalid с причиной, без тихой замены
и без изменения первоначального denominator. Новая версия набора — отдельный запуск.

### Текущее поручение: пять случайных новых вопросов

Из 20 подготовленных holdout отобрать пять с dependency = null,
new_conversation = true и разными intent/sequence groups. Сохранить seed, допустимый
pool, алгоритм, пять IDs и порядок до первого вызова; не выбирать по ответам модели.
Матрица остаётся побайтно прежней. Цепочки с обязательным префиксом в эту выборку
не входят, поэтому дополнительные anchor generations не нужны. Четыре pilot и
оставшиеся 15 holdout сейчас не запускаются. Полный набор — отдельное расширение
объёма по поручению пользователя, без общего walltime deadline или общего call cap.

## Реализация и проверки

1. **Astra/root:** проверить originals и freeze 24-case manifest; готовить всё без
   inference до готовности проверок; затем freeze отдельной выборки пяти вопросов.
   Публичный manifest содержит только безопасные поля.
2. **Sol TDD:** RED→GREEN для shared-A pairing, запрета gold в model payloads,
   source/history identity стадий, bounded context, critic schema/refs, одной repair,
   invalid/length/insufficient_evidence, точного учёта всех calls/time и restart без replay.
   Atomic checkpoints с простыми статусами и зависимостями, без FSM framework.
   Dry-run целого runner с mock network проверяет counts/partial/resume и privacy.
3. **Luna → Sol → Astra:** независимые reviews runner/spec/tests до live; исправления
   перепроверены. Старый full-chat baseline и protected artifact hashes сохранены.
4. **Текущий запуск после reviews:** пять выбранных новых holdout под общим lock,
   с замороженным protocol hash; без автоматического добавления pilot. Если протокол
   окажется непригодным, сохранить FAIL и не адаптировать его по этим holdout ответам
   под видом прежнего эксперимента. Изменение протокола — новая версия и явный отчёт.
   **Для отдельно порученного будущего полного набора:** четыре pilot под общим lock,
   измерить stage bytes/time/tokens, proportion repair/recheck и parsing/budget failures.
   Сейчас pilot не запускать. При системной непригодности протокола сохранить причину,
   сделать targeted repair и перепроверить затронутый pilot; все дополнительные calls
   учитываются, исходные FAIL не стираются. Protocol hash freeze перед holdout.
5. **Выбранный holdout:** выполнять пять пар последовательно в зафиксированном
   порядке с соблюдением dependencies. Case checkpoint содержит resolved query,
   selected+transmitted evidence, common prefix, A, critique, optional repair/recheck,
   hashes и stage metrics. До завершения выбранных пяти без общего deadline или общего call cap;
   при реальной ошибке/прерывании — pending/unavailable и resume с теми же hashes,
   без скрытого повтора неоднозначно отправленного вызова.
6. **Независимый source audit:** все завершённые holdout пары, отдельно pilot; gold
   группы и original spans доступны assessor, critic verdict скрыт до оценки.
   Автоматические технические метрики плюс ручная агентская семантическая рубрика;
   disagreements/ограниченный контекст → NOT PROVEN. Astra проверяет итог/регрессии;
   quality результат не выдаётся за человеческую приёмку или готовность live correction.

## Время и отчёт

Три прежних real receipts: generation 37.98/49.31/41.22 s, total
39.95/51.13/43.08 s. **Грубая оценка**, если новые стадии стоят столько же:
для текущих пяти 5×2..4 calls = 10..20, примерно **6–17 минут**, плюс
orchestration/assessment; unknown без generation/error может сократить число стадий.
Это не измерение новых стадий и не лимит исполнения. Для отдельно разрешённого
полного набора 24×2..4 calls = 48..96, примерно **32–82 минуты**, плюс assessment.
В подготовленном наборе один кейс должен дать уточнение без генерации: при этом
23×2..4 = 46..92 calls, примерно **31–79 минут**; другие unknown/error могут сократить
число стадий. Это расчёт сценария, не прогноз точного времени или гарантированный минимум.
Pilot четыре входит в 24, дополнительно не прибавляется. Critic/repair могут работать
дольше, особенно при длинном выводе; эти средние не являются гарантией длительности.
Общего лимита длительности по указанию пользователя нет. После будущего pilot
показать фактическую оценку остатка; сейчас эти стадии ещё не измерялись.

Показать selected = 5 из pool = 20, eligible/completed pairs из выбранных пяти,
pending/invalid/dependency-blocked внутри выборки и 15 unselected/not_run отдельно,
strict wins/regressions/ties, числители/знаменатели всех quality показателей,
macro completeness по кейсам и по intent groups, retrieval coverage, false acceptance
критика; для отсутствующего repaired answer качество unknown, доступность считается.
Полнота: covered / N обязательных gold-групп, где covered требует всех обязательных
частей. Partial даёт 0 в числителе и отдельно описанные покрытые/пропущенные части;
missing/unverifiable также выводятся отдельно, N = 0 означает not_applicable.
На общих оценённых A/B случаях выводить сумму covered / сумму N и macro; неоценённые
ответы обозначать отдельно. Сравнивать части даже при partial → partial. Атомарные
утверждения реального ответа для correctness/support выделять независимо: 50 групп
не означают 50 атомарных claims. Итог пяти — предварительный, без вывода по всем 20.
Median/p90 наблюдаемой A/B latency на общих завершённых парах, все ошибки/timeouts и
общие затраты отдельно; warm/cold не смешивать в заявленное ускорение. Не выдавать
таймауты за быстрые ответы. Деньги API не выдумывать: локальных paid-provider calls 0,
электричество и цена оборудования не измерены. Токены/usage ролей только если сообщены.
