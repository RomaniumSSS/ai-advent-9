# Day 20 — план реализации

Статус: план для реализации, 28.09.2026. Источник требований —
[`SPEC.md`](SPEC.md), текущая рабочая редакция с Qwen3.8 27B. План относится
только к самостоятельной папке `day20/`; Day 18 продолжает отправлять сводку,
а сданный Day 19 не меняется и не импортируется во время запуска Day 20.
Детальные отметки выполнения принадлежат [`TASKS.md`](TASKS.md).

## Решение и границы

- Один исследовательский агент работает локально через CLI и через входящий
  Telegram-чат. Telegram — интерфейс, не MCP-сервер. На каждом модельном ходе
  Qwen получает каталог разрешённых инструментов двух независимых MCP-серверов.
  Harness проверяет предложение, направляет его по сохранённому соответствию
  имени и сервера, возвращает результат с тем же `tool_call_id` и передаёт
  новое observation модели. Первый вариант принимает один MCP-вызов за ход;
  остальные предложения получают явный результат отказа и учитываются в лимите.
- У Day 20 собственное SQLite-хранилище для запросов, связей сообщений,
  article snapshots, входящих update и попыток доставки. Снимок полного текста
  фиксирует URL, время, hash, длину и выданные части: смена stdio-соединения
  или перезапуск не смешивают версии статьи. В trace хранятся ссылки на
  ограниченные публичные выдержки, а не секреты, личный текст или скрытые
  рассуждения модели.
- Habr MCP предоставляет ограниченный поиск по RSS-профилю Day 19 и чтение
  статьи по каноническому HTTPS-URL. Чтение допускает URL вне RSS-окна,
  ограничивает редиректы, размер и время загрузки, сохраняет снимок и выдаёт
  текст частями с признаком завершения. GitHub MCP — официальный сервер
  закреплённой версии в read-only режиме; доступный модели список сужен до
  проверенных read tools. Конфигурация запуска и секрет GitHub не передаются
  Habr-серверу и модели. [Официальная документация GitHub MCP](https://github.com/github/github-mcp-server/blob/main/README.md)
  описывает read-only и выбор tools; конкретный выпуск и SDK ещё проверяются.
  Текст статьи, README и issues передаётся модели как недоверенные данные,
  а не как новые инструкции или разрешение на действия.
- В каталоге модели имена получают префикс сервера; таблица alias → исходное
  имя, схема и конфигурация фиксируется после discovery. Аргументы проверяются
  по обнаруженной схеме до `call_tool`; `structured_content`, текстовые и
  поддерживаемые resource blocks приводятся к ограниченному observation.
  `isError`, неподдерживаемый тип и превышение размера дают явную ошибку.
  Таймаут каждого сервера ограничен отдельно; исполняются только чтение
  источников и выдача ответа, без запуска кода или изменения репозиториев.
- Профиль модели — только `qwen/qwen3.8-27b` через OpenRouter/DeepInfra,
  `tool_choice=auto`, без fallback и SDK retry. До старта и перед каждым
  следующим вызовом резервируется консервативная верхняя стоимость по текущему
  тарифу, размеру входа и пределу выхода. Если `usage.cost` отсутствует,
  резерв не списывается как ноль. Лимиты: ≤10 модельных обращений, ≤8
  предложенных MCP-вызовов и ≤$0.25 за запрос. Нет автоматического перехода
  на DeepSeek при отказе Qwen.
- Итог модели проходит отдельную проверку: ссылки на источники должны
  соответствовать сохранённым observations; `verified` требует полного
  чтения статьи и подтверждённой связи с проверенным репозиторием.
  `limited` явно называет недостающий источник. Автоматическая проверка
  устанавливает структуру и полноту доказательств; смысл существенных
  утверждений в реальном прогоне сверяется отдельно человеком.
  Если связь репозитория со статьёй сомнительна, чат запрашивает ссылку либо
  подтверждение пользователя; похожее имя само по себе не доказывает связь.
- Входящий poller принимает только разрешённые chat/user ID и проверяет,
  что reply действительно указывает на сообщение этого бота. Для двух
  ссылок он сохраняет кандидатов и ждёт выбор. Если личная цель не названа,
  задаётся один короткий вопрос до рекомендации. Один получатель обновлений
  обеспечивается проверкой webhook и локальной блокировкой процесса.
  Контекст продолжения — выбранный проект, явная цель и краткий предыдущий
  итог. Day 18 остаётся
  только исходящим отправителем; его БД и FSM не читаются.
- Стадии исследования — `received → running → answer_ready`, исходы
  `needs_clarification`/`failed`; полнота ответа — `verified`/`limited`.
  Отдельная доставка — `pending/delivered/unknown/failed`. Это минимальное
  состояние для возобновления запроса и исключения двойного ответа; цена —
  транзакции и проверка переходов. Неизвестный исход отправки не повторяется
  автоматически.

## Зависимости и остановки

P0 — ранний технический шлюз для GitHub; P1 и P2 строят источники и транспорт,
P3 потребляет их, P4 подключает чат к готовому локальному агенту. P5 предшествует
любым платным проверкам P6; P7 начинается после доказанного локального сценария.
Проблема совместимости GitHub блокирует P2/P6, но не разработку Habr, store и
офлайн-клиента. При недоступности Qwen или превышении бюджета P6 не меняет
модель/провайдера автоматически. Если webhook либо другой poller уже активен,
не запускать приём обновлений до согласования одного получателя.

`TASKS.md` — подробный трекер. `todo.md` сохраняет лишь текущий результат,
ссылку на доказательство, следующий шаг и блокер. В выполненных проверках
отдельно указывать offline, реальные MCP, реальную модель и Bot API;
человеческое подтверждение не выводить из mock-тестов.
