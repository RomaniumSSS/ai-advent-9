# Day 20 — исследование проекта из сводки через несколько MCP-серверов

Статус: рабочая спецификация для реализации, 28.09.2026. Основа — задание AI Advent
«День 20. Orchestration MCP» (сообщение #3917 от 25.09) и уточнение автора
#3929: цепочка должна работать с несколькими MCP-серверами и схемами их
инструментов. Telegram-чат и исследование проектов — выбранный нами сценарий,
а не обязательные пункты задания курса.

Совместимость сверена с кодом Day 19 на коммите
8c3aac3b5efbd197da79e06121a0588887a9ce2b. Day 20 — самостоятельная папка:
сданный Day 19 не меняется, его файлы и SQLite не становятся runtime-зависимостью.
Под «совместимостью» здесь понимаются перенос проверенных принципов агентного
цикла и RSS-валидации, явное описание изменившихся контрактов и отсутствие
регрессии Day 19, а не возможность запустить его агент без доработок.

## Результат для пользователя

Бот продолжает присылать ежедневную сводку статей об ИИ-агентах. Пользователь
отвечает на неё, например: «Сверь GitHub проекта и предложи, где он пригодится
мне для диагностики Linux VPS». Агент читает полную статью через Habr MCP,
находит связанный с ней репозиторий и проверяет его через отдельный GitHub MCP.
В ответе он отделяет сведения из статьи от того, что увидел в репозитории,
предлагает конкретную пробу для задачи пользователя и указывает ограничения.

Первый ответ не обязан проверять GitHub для каждой статьи ежедневной сводки:
углублённое исследование запускается по запросу в чате. Можно также начать
отдельный запрос со ссылкой на статью или поиском по доступной ленте Хабра.
Тот же исследовательский запрос можно запустить локально без Telegram, чтобы
проверить оркестрацию отдельно от доставки.

## Модель Day 20

Первая модель для реализации и реального прогона — `qwen/qwen3.8-27b` через
OpenRouter с `provider.only=["deepinfra"]`, `allow_fallbacks=false` и
`max_retries=0`. Профиль принадлежит Day 20: настройки и ограничение Day 19
на DeepSeek не импортируются. DeepSeek не является автоматическим запасным
вариантом для запроса Day 20. Если выбранный endpoint недоступен, запрос
завершается явной ошибкой, без тихой смены модели или провайдера.

На 28.09.2026 [каталог endpoint OpenRouter](https://openrouter.ai/api/v1/models/qwen/qwen3.8-27b/endpoints)
показывает для Qwen на DeepInfra
поддержку `tools` и `tool_choice=auto`; тариф — $0.15 за миллион входных и
$1.875 за миллион выходных токенов. Перед первым платным прогоном профиль,
тариф и верхнюю оценку расхода проверяют заново. Поддержка function calling
подтверждает совместимость интерфейса, но качество выбора между Habr и GitHub
MCP устанавливается только прогоном сценариев Day 20.

## Обязательное ядро Day 20

1. Один агент регистрирует **минимум два независимых MCP-сервера**: локальный
   Habr MCP Day 20 с данными статей и отдельный официальный GitHub MCP с
   данными публичных репозиториев. У каждого — собственная конфигурация и
   обнаруженный каталог схем; повторное stdio-соединение между вызовами
   допустимо, если оно не теряет необходимое состояние.
2. Harness объединяет разрешённые инструменты в каталог для модели, хранит
   однозначное отображение `инструмент → сервер/конфигурация`, проверяет аргументы
   по схеме и отправляет вызов на правильный сервер. Одинаковые имена инструментов
   на разных серверах не создают неоднозначной маршрутизации. Схема GitHub
   tools не дополняется обязательным для Day 19 полем run_id.
3. Модель сама выбирает следующий инструмент по запросу и предыдущему
   observation. Результат вызова возвращается модели с исходным `tool_call_id`;
   следующий шаг зависит от полученных данных. Harness не содержит обязательной
   последовательности вида `Habr → README → issues` и не имитирует вызовы MCP.
4. В демонстрационном исследовательском запросе инструменты обоих серверов
   реально используются в нескольких последовательных ходах. Trace фиксирует
   сервер, инструмент, call ID, проверенные аргументы, статус, время и
   ссылку и hash ограниченного снимка observation без секретов и личного
   текста. Публичные выдержки источников сохраняются отдельно в пределах
   размера, нужного для аудита утверждений. По trace можно восстановить
   выбор и порядок вызовов.
5. Клиент принимает как структурированный результат Day 20 Habr MCP, так и
   поддерживаемые текстовые/ресурсные блоки GitHub MCP. Он проверяет MCP
   isError, тип и размер результата; неподдерживаемый блок даёт явную ошибку,
   а не пустое успешное observation. Версию GitHub MCP, фактические схемы
   выбранных read-only tools и совместимость с MCP SDK проекта проверяют
   прямым discovery/call до реального модельного прогона.

## Данные и инструменты

- Habr MCP Day 20 даёт ограниченный поиск по тому же RSS-профилю, что и Day 19,
  и отдельное чтение конкретной канонической статьи по URL, в том числе статьи
  вне текущего RSS-окна. Текст статьи и исходящие GitHub-ссылки извлекаются
  из её страницы, а не из 600-символьной RSS-выдержки Day 19. Длинный текст
  доступен модели ограниченными частями с явным продолжением; признак
  полного чтения допустим только после получения всех частей. Результат
  содержит URL, момент чтения и границу объёма. При недоступности или
  обрезке текста агент не утверждает, что проверил всю статью. Сетевое чтение
  принимает только канонические HTTPS-URL статей Habr и ограниченные ответы;
  исходящие ссылки извлекаются как данные, но не загружаются этим MCP.
- GitHub MCP запускается с read-only ограничением; harness допускает только
  обнаруженные инструменты чтения. Агент читает README выбранного публичного
  репозитория и при необходимости проверяет релизы, лицензию, открытые
  проблемы или другую доступную метаинформацию. Набор вызовов зависит от
  вопроса; отсутствие данных не заменяется догадкой. Доступ к другим
  репозиториям без связи с запросом не нужен. Секрет доступа, если он
  потребуется выбранной версии сервера, доступен только GitHub MCP и не
  попадает в Habr MCP, запрос модели, trace или чат.
- Связь статьи с репозиторием подтверждается прямой ссылкой в статье либо
  явным встречным указанием в репозитории. Поиск по похожему названию может
  дать кандидата, но не доказанную идентичность проекта; для сомнительного
  кандидата бот просит ссылку или подтверждение пользователя.
- В ответе у каждого существенного утверждения есть понятная опора: статья,
  репозиторий или явно помеченный вывод агента. Сведения автора статьи не
  становятся независимо проверенными только потому, что найден GitHub.
  Третий MCP для общей веб-верификации в этот объём не входит.
- Текст статьи, README и issues считается данными, а не инструкциями агенту.
  Запуск кода проекта, установка пакетов, изменение репозитория и другие
  внешние действия в инструменты Day 20 не входят.

## Чат и выбор контекста

1. Telegram — интерфейс ввода и доставки, **не третий MCP-сервер**. Day 20
   использует уже существующего бота и разрешённые chat_id и user_id. Его входящий
   обработчик и состояние живут отдельно от FSM ежедневной сводки Day 18.
   Day 18 и сданный Day 19 не меняются; Day 20 не импортирует их код и не
   читает их SQLite. Контекст сводки берётся из сообщения, на которое ответил
   пользователь.
2. Бот принимает ответ на сообщение со сводкой, отдельную команду
   `/research` со ссылкой или вопросом и обычное сообщение с прямой ссылкой
   на статью Хабра. После доставленного ответа Day 20 обычный текст без ссылки
   продолжает последний проект и без Telegram reply; `/research` начинает новый.
   Связь сообщения, выбранной статьи,
репозитория и ответа сохраняется. Для продолжения передаются выбранный
   проект, явно сообщённая цель и краткий итог предыдущего ответа, а не вся
   история чата.
3. Сводка Day 18 сейчас является **одним сообщением с максимум двумя ссылками**.
   Если ответ на неё явно указывает URL или номер статьи, выбирается он. Если
   пользователь пишет «этот проект» при двух возможных статьях, бот сначала
   спрашивает, какую выбрать. При отсутствии доступного текста исходного
   сообщения бот просит ссылку. Случайный репозиторий по совпадению названия
   не выдаётся за проект из статьи. При уточнении сохраняются оба кандидата
   и исходный вопрос; ответ «1» или «2» продолжает именно этот запрос.
4. Для фразы «пригодится мне» агент использует только цель и ограничения,
   сообщённые пользователем в текущем запросе или явном контексте беседы.
   Если этого недостаточно для личной рекомендации, бот задаёт один короткий
   уточняющий вопрос, сохраняя уже выбранный проект. Постоянный профиль
   пользователя для первого варианта не обязателен; инфраструктуру и
   интересы нельзя выдумывать.
5. Входящие Telegram `update_id` и `(chat_id, message_id)` сохраняются до
   подтверждения offset, чтобы повторная доставка не запускала второй анализ.
   У бота должен быть ровно один приёмник обновлений; для первого варианта
   выбран один процесс long polling в разрешённом приватном чате. Отправка
   Day 18 остаётся исходящей и не конкурирует за получение обновлений.
   Перед запуском проверяется отсутствие активного webhook; его нельзя
   отключать молча ради polling.
   Исходящие ответы связываются с запросом; неопределённая доставка не
   повторяется вслепую.

Чат, сообщения, исследовательский запрос и попытка доставки — отдельные
сущности. У запроса хранятся источник, выбранная статья и репозиторий,
явно сообщённая цель, ID запуска и ссылка на безопасный trace. Исследование
проходит минимальные стадии `received → running → answer_ready`, с исходами
`needs_clarification` и `failed`; готовый ответ отдельно помечается как
`verified` либо `limited`. Доставка готового ответа имеет собственные
состояния `pending / delivered / unknown / failed` и подтверждается Telegram
message_id. Так готовый ответ не выдаётся за доставленный, а частичный,
но честный ответ не выдаётся за провал. Цена этой схемы — отдельные записи
запроса и доставки и проверка переходов; польза — восстановление после сбоя
и снижение риска двойных ответов. Это не меняет FSM Day 18 и не требует общего
движка FSM.

## Содержание ответа и ошибки

Ответ с полнотой `verified` допустим после полного чтения статьи и
реальной проверки подтверждённого публичного репозитория. Он содержит
ссылки на оба источника и кратко описывает, что проект реально предлагает,
где он может пригодиться для названной задачи, какой небольшой безопасный
эксперимент сделать первым и что осталось непроверенным. Сведения GitHub
привязаны ко времени чтения и, где доступно, к ref/commit. Формулировки
«по словам автора», «проверено в репозитории» и «моя рекомендация» не
смешиваются. Если проект нерелевантен, агент говорит об этом прямо.

Если GitHub-ссылка отсутствует, связь с найденным репозиторием сомнительна,
полный текст недоступен или GitHub MCP отказал, агент сообщает конкретное
ограничение и, если осталось достаточно оснований, готовит ответ с полнотой
`limited`. Он точно указывает, какая часть проверки состоялась: например,
сведения GitHub можно назвать проверенными, даже когда полный текст статьи
недоступен, но нельзя утверждать, что проверена связь проекта со статьёй.
Если нет оснований для полезного ответа, запрос становится `failed`;
ошибка сервера, неверная схема, таймаут и исчерпание бюджета не
превращаются в `verified`.
На один исследовательский запрос допускается не более 10 обращений к модели
и 8 предложенных MCP-вызовов, включая отклонённые. Бюджет реального запроса
не превышает $0.25; перед запуском консервативная верхняя оценка по текущему
профилю Qwen должна укладываться в этот предел. Перед каждым следующим
обращением к модели учитываются уже потраченная сумма, размер нового контекста
и верхний предел выходных токенов; ход не начинается, если остатка бюджета
недостаточно. Время и размер каждого observation также ограничены
конфигурацией. Лимиты 6/5 из Day 19 не копируются
механически; отсутствие reported cost не трактуется как нулевая стоимость.

## Проверка и сдача

1. После реализации Day 20 прежние тесты Day 19 проходят без изменения его
   кода, файлов результата и БД. Если для GitHub MCP понадобится изменить
   общий пакет MCP, до такого изменения отдельно доказывается совместимость
   с Day 19 либо для Day 20 выбирается изолированное окружение.
2. Офлайн-проверки используют управляемую модель и два отдельных MCP-сервера.
   Проверяются discovery, маршрутизация при совпадении имён, реальные
   call_tool на обоих соединениях, передача observation с тем же call ID,
   структурированные и текстовые/ресурсные результаты, MCP isError,
   разные наборы инструментов для разных вопросов, отказ сервера и пределы
   вызовов, закрепление Qwen/DeepInfra и отсутствие fallback. Ни один write
   tool GitHub не попадает в разрешённый каталог.
   Fake provider не считается проверкой качества реальной модели.
3. Отдельно проверяются прямой URL вне RSS-окна, чтение длинной статьи
   несколькими частями, запрет метки `verified` при пропущенной части,
   отсутствие подтверждённой связи с GitHub, неоднозначная сводка с двумя
   ссылками, уточнение личной цели, продолжение беседы после перезапуска,
   повтор одного Telegram update и неизвестный результат отправки.
   Утверждения и статус полноты ответа соответствуют доступным источникам.
4. До платного прогона прямой клиентский тест подключается к выбранной версии
   официального GitHub MCP с текущим SDK проекта, получает схемы разрешённых
   инструментов и читает публичный README. Несовместимость протокола или
   формы результата останавливает интеграцию; успешный fake server её не
   подменяет.
5. Ограниченный прогон с реальной Qwen3.8 27B на закреплённом DeepInfra и
   настоящими Habr/GitHub MCP показывает **в одном запросе** чтение статьи,
   README и ещё одну уместную проверку репозитория. Модель выбирает порядок;
   trace доказывает вызовы
   обоих серверов, зависимость следующего выбора от observation и источники
   опубликованных выводов. Момент чтения и предел охвата сохранены.
6. Через настоящий Bot API отдельно проверяется путь пользователя:
   сводка Day 18 → ответ в Telegram → уточнение при неоднозначности либо
   исследование → доставка в тот же чат → последующий вопрос с сохранённым
   контекстом. Видео показывает живой запрос,
   видимые вызовы разных серверов и итоговый ответ; код и README объясняют
   запуск и границы доказательств. Секреты и скрытые рассуждения модели в
   trace, видео и репозитории не сохраняются.

Публикация кода, деплой обработчика Telegram и отправка работы на курс —
отдельные действия после реализации и проверки, а не следствие этого документа.

Основание для конфигурации GitHub MCP: [официальный сервер GitHub](https://github.com/github/github-mcp-server/blob/main/README.md)
документирует read-only режим и ограничение каталога инструментов. Наличие
этих возможностей в выбранной версии не заменяет прямую проверку пункта 4.
