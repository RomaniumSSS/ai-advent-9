# Day 20 — один агент, два MCP и входящий чат

Локальный Habr MCP ищет статьи в фиксированной RSS-ленте и читает конкретную
статью целиком по каноническому HTTPS-URL. Отдельный официальный GitHub MCP
v1.12.2 работает в режиме `--read-only`; агенту открыты только
`get_file_contents`, `get_latest_release` и `list_issues`. Qwen3.8 27B через
OpenRouter/DeepInfra выбирает нужный инструмент после каждого observation.
Telegram — интерфейс ввода/доставки того же агента, не третий MCP.

Day 20 не импортирует Day 18/19 и использует собственную SQLite в
`day20/data/day20.db` либо в `DAY20_DATA_DIR/day20.db`, если каталог задан
для VPS. Код и БД сданного Day 19 остаются без изменений.

## Подготовка

1. Установить зависимости репозитория: `uv sync`.
2. Скачать официальный `github-mcp-server` [релиза v1.12.2](https://github.com/github/github-mcp-server/releases/tag/v1.12.2)
   под свою ОС, сверить SHA-256 с checksums того же релиза и указать полный путь
   к исполняемому файлу в `DAY20_GITHUB_MCP_COMMAND`. На macOS arm64 проверен
   архив с SHA-256 `7e6c5aec43f26b82d3580e77a4ee26872bcd34b48c9a08d0eaef48b5d0563904`.
   Запущенный Docker или Go не нужны.
3. Задать `OPENROUTER_API_KEY` через окружение. Для публичного GitHub MCP
   нужен `DAY20_GITHUB_TOKEN` или локальная авторизация `gh auth login`.
   Токен передаётся только процессу GitHub MCP. Значения переменных в README,
   trace и коммиты не вносить.

Локальный запрос:

```bash
uv run python -m day20.cli research \
  --article https://habr.com/ru/articles/1007122/ \
  --goal 'диагностика Linux VPS' \
  'Сверь проект из статьи с GitHub и предложи безопасную первую пробу'
```

Если конкретной ссылки нет, её можно опустить: агент использует ограниченный
поиск в той же RSS-ленте. `/research <вопрос>` в чате запускает такой же поиск;
пустая команда просит ссылку. Поиск не охватывает весь Хабр.

Для входящего чата нужен **тот же** `DAY18_TELEGRAM_BOT_TOKEN`, а также
`DAY20_TELEGRAM_CHAT_ID` и `DAY20_TELEGRAM_USER_ID` разрешённого приватного
чата. Затем: `uv run python -m day20.cli poll`. Перед long polling процесс
проверяет отсутствие webhook и берёт OS lock; второй receiver запускать нельзя.
Day 18 остаётся исходящим отправителем сводки. Бот принимает reply на неё,
`/research` со ссылкой, обычное сообщение с прямой ссылкой на статью Хабра и
ответы на уточнение/предыдущий результат Day 20. После доставленного ответа
обычный текст без ссылки продолжает последний проект даже без Telegram reply;
`/research` начинает новое исследование. До первого ответа прочие сообщения
отмечаются как обработанные без ответа.
Если пользователь указывает отдельный GitHub URL, бот просит подтвердить
связь с выбранной статьёй; ответ помечает это как подтверждение пользователя,
а не как ссылку, найденную в статье.
Никакие webhook не отключаются автоматически.

На VPS проверен изолированный Python 3.12 venv с `mcp==2.2.0`,
`openai==3.6.0`, `jsonschema==4.26.0`. Код и официальный бинарник GitHub MCP
лежат отдельно от Day 18; `DAY20_DATA_DIR` указывает на доступный сервисному
пользователю каталог. Для запуска `python -m day20.cli poll` нужны переменные
выше, причём env-файл хранится вне репозитория с правами 600. Запускать только
один poller для этого токена: Bot API `getUpdates` не распределяет сообщения
между конкурирующими получателями. Результат VPS preflight — в
[`results/vps-readiness.md`](results/vps-readiness.md).

`uv run python -m day20.cli audit REQUEST_ID` выводит безопасный trace. Его
порядок model/tool, server, call ID, статус, hash и время можно сопоставить с
публичными выдержками в закрытой для Git папке `day20/data/evidence/`.
Исходящие ответы имеют собственный статус доставки; после неизвестного исхода
отправки повтор не выполняется автоматически. `verified` означает технически
подтверждённое полное чтение статьи и README связанного публичного репозитория;
смысловые утверждения реального ответа требуют отдельной ручной сверки.

## Проверки

```bash
uv run python -m unittest day20.test_offline -q
uv run python -m unittest day19.test_offline day19.test_report_evidence -q
```

Результаты fake-модели/Bot API, прямые вызовы настоящего MCP, реальный Qwen и
[живой путь Telegram](results/telegram-live.md) учитываются отдельно в `results/`.
[Видео нового живого запроса](demo/telegram-live.mp4) показывает входящий
вопрос, вызовы обоих MCP и доставку ответа; [evidence и ограничения записи](results/telegram-video.md)
содержат trace и протокол проверки.
При недоступности
источника, ошибке MCP, пределе вызовов или недостаточном бюджете агент не
выдаёт `verified`. Длинные GitHub-ответы сверх 36 KiB дают явную ошибку;
веб-проверка за пределами статьи и репозитория в эту версию не входит.
