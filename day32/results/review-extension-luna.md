## Открытые замечания

🔴 **[BLOCKER — границы публикации]** `day32/video/run_demo.py:116–121,180` — сценарий проверяет PR, имя head-ветки и совпадение локального HEAD с PR, но перед публикацией не проверяет, куда ведёт `origin`. Фактический push всегда идёт в `origin`, который может указывать на другой репозиторий, чем `--pr-repo`. Тогда корректный PR/worktree пройдёт preflight, а учебные коммиты будут опубликованы в посторонний remote. **Воспроизведение:** настроить у чистого локального worktree remote `origin` на другой репозиторий, сохранив branch name и HEAD, совпадающие с настоящим PR в `--pr-repo`; preflight проверяет GitHub через `gh` и проходит, а `git push origin ...` отправляет в заданный `origin`. **Исправление:** получить URL `origin` и владельца/репозиторий head PR, сравнить их с разрешённым репозиторием до создания любого commit; отклонять несовпадение. Ещё надёжнее передавать проверенный URL в сам `git push`, не полагаясь на изменяемый alias `origin`. Также закрепить ожидаемые `day32-pr-review`/`day32-demo-limit10`, поскольку разрешение распространяется на эти две ветки и один PR.

🟡 **[WARNING — бюджетная остановка скрывается в итоговом статусе]** `day32/video/run_demo.py:195–201,231–252` — записи `budget_blocked` не имеют `report`, поэтому фильтр `if r['report']` удаляет их из показанных и записанных в `manifest['outcomes']` результатов. После `done['blocked']` сценарий только пишет событие `stopped_budget` и прерывает цикл кейсов, затем продолжает SIMULATED-часть и безусловно выставляет `manifest['status'] = 'scenario_completed'`. При этом манифест не показывает, что live-сценарии остановились из-за бюджета, и не включает саму блокировку. **Воспроизведение:** использовать отдельный тестовый state с уже занятым резервом так, чтобы очередной snapshot вернул `budget_blocked`; `done.json` получает `blocked=true`, но запись не попадает в `outcomes`, а итоговый manifest всё равно говорит `scenario_completed`. **Исправление:** сохранять outcome для каждой строки, включая `report=None` (`status`, trace_id, head, mode); отобразить budget-blocked запись в UI/кадре; выставлять отдельный итоговый статус вроде `budget_stopped` и хранить число реально завершённых live-кейсов.

## Что проверено

При одинаковом `--state` dry-run и record используют один существующий SQLite ledger: сценарий не удаляет его и запускает watcher/Runner с тем же путём. Лимит передаётся в `Runner`, который резервирует средства атомарно; блокировка завершает watcher до следующего mode/case. В этом смысле резерв не сбрасывается между режимами. Текущий ledger существенно ниже лимита, но будущие расходы здесь не прогнозировались.

Для каждого head watcher получает snapshots через `poll()` настоящего PR и пропускает остальные PR/SHA; Runner выполняется для выбранного режима, а повторный вызов того же режима проверяет dedupe. На каждый новый case создаётся новый commit/SHA. Модельный клиент и режимы в сценарии используют существующий single-request/no-fallback runner. Новые PR-файлы и тесты не запускаются; тесты явно маркируют fault provider как SIMULATED. UI использует `textContent`, только GET endpoints и bind на `127.0.0.1`.

Все ожидания в сценарии ограничены циклом старта браузера, watcher deadline 750 секунд на head и конечными паузами; бесконечного ожидания ответа нет. При исключении выставляется `interrupted`, сырой WebM обычно сохраняется после закрытия контекста. Отдельный риск очистки: операции внутри `finally` последовательны, поэтому исключение из `context.close()`/`video.path()` пропустит завершение дочерних web-процессов и финальную запись manifest; этот путь тестами не покрыт.

39 офлайн-тестов проверяют Git snapshots, seeded 100 property checks, ошибки/дедупликацию/резервы и SIMULATED отчёты. Они не тестируют CLI guards и публикацию `run_demo`; эти тесты не заменяют ни этот аудит destination, ни live-trigger/ручной осмотр записи. Usage/cost этого ревью не измерялись.
