# Day27 — задачи

Требования: [SPEC.md](SPEC.md). Статус отметок — только по свежим проверкам;
планирование и код разрешены параллельно, отдельный просмотр письменной спеки ещё не состоялся.

- [x] **T1 — зафиксировать объём и сценарий.** Проверены корень worktree,
  ветка `day27-local-app`, локальные инструкции и условие #4766. Созданы SPEC и
  [SCENARIO](video/SCENARIO.md); Day01–26 остаются неизменными.
- [x] **T2 — HTTP/stream/history через TDD.** Сначала воспроизвести требования
  падающими тестами на локальной заглушке, затем реализовать контракт. Проверить
  `/api/chat`, свободный ввод, модель, порядок истории, потоковые части и настоящий
  финал; пустой/некорректный запрос, недоступный upstream, ошибка модели, неверный JSON
  и EOF без `done` не проходят как успех. Не вызывать реальную модель из mock-тестов.
- [x] **T3 — самостоятельное приложение.** Python standard library backend
  на `127.0.0.1:8067`, фиксированная локальная Ollama, веб-чат с вводом, потоковым
  ответом, историей в памяти и «Новый чат». Проверить, что после сброса старых
  сообщений нет в следующем payload, ошибка не добавляет успешную реплику,
  UI восстанавливает управление, нет облачного fallback и импортов других дней.
- [x] **T4 — наблюдаемый результат.** Связать request ID с окончанием и
  фактическими метриками; сохранять полный ввод, переданный контекст, ответ и ошибку
  в отдельный каталог каждого контролируемого демо-прогона. Обычная история чата
  остаётся в памяти браузера. Не подменять отсутствующие метрики нулями.
- [x] **T5 — повторяемый живой сценарий.** Подготовить один скрипт действий
  для сухого прогона и записи. Выполнить три запроса из SCENARIO на установленной
  `qwen3:8b`, последовательно; сохранить actual outputs и отдельно оценить историю,
  арифметику и выполнение инструкции. Исправить обязательный сбой перед записью;
  смысловую ошибку модели явно документировать, без подмены ответа фикстурой.
- [x] **T6 — живая запись.** Новый изолированный browser context, новые реальные
  запросы, отдельный каталог дубля. Ждать финал конкретного request ID; показывать
  ответы и метрики. Закрыть свой context в `finally`, сохранить исходное видео;
  проверить `ffprobe` и прочитать кадры начала, трёх ответов и конца.
- [x] **T7 — результат для проверки.** README с командами, RESULT/RELEASE_NOTES
  с фактическими проверками, метриками, ограничениями и ссылками на видео/журналы.
  Проверить diff и неизменность сданных дней. Ответственный обновляет короткий
  root `todo.md`; публикация и сдача не отмечаются по одному наличию файлов.

Порядок: T2 → T3/T4 → T5 → T6 → T7. T1 и подготовка кода идут параллельно
по команде пользователя. Планировщик владеет только SPEC/TASKS/SCENARIO;
исполнитель — кодом и тестами, ответственный — общими статусами и итоговой проверкой.
Моки, локальные живые ответы и проверка видео фиксируются раздельно.
