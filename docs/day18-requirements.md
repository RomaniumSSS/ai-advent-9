# День 18 — требования для новой спецификации

Это зафиксированные требования и выбор пользователя. Нормативная SPEC и
реализация находятся отдельно; решения ниже обновлены 27.09.2026.

## Из задания и уточнений автора

- Нужен отложенный или периодический запуск агента без нового сообщения
  пользователя. Автор уточнил: по расписанию запускается агент, а не отдельный
  специализированный worker; предпочтительный триггер — cron.
- Внутри запуска модель обращается к созданному для задания MCP-инструменту;
  harness проверяет и исполняет вызов, затем возвращает модели результат.
- MCP-инструмент сохраняет полученные данные в JSON или SQLite и выдаёт
  агрегированный результат. Агент использует его для периодической сводки.
- Для сдачи нужны работающий код и видео, показывающее выполнение по расписанию.

## Выбранный сценарий

- Запускать на своём VPS ежедневно в 18:00 по `Europe/Warsaw`.
- Мониторить Хабр на предмет практического применения ИИ-агентов в работе и
  личных задачах, не ограничиваясь проектами пользователя. Один выпуск
  анализирует до 20 статей из текущего RSS и сохранённой очереди; это лимит
  анализа, а не чтения и сохранения RSS.
- Автоматически доставлять сводку в заранее указанный Telegram-чат. Бот и
  адресат настроены; реальная отправка подтверждена cron-запуском 27.09.
- В каждом ежедневном Telegram-отчёте показывать не более двух статей.
  Это лимит публикации одного отчёта, не лимит чтения RSS или сохранения
  наблюдений; если после сбоя в один календарный день отправятся несколько
  отдельных отчётов, лимит применяется к каждому. В первую очередь показывать
  подтверждённые описанием кейсы; возможные кейсы допустимы только
  с явной пометкой, если подтверждённых меньше двух.

## Требуемые свойства результата

- Успешный плановый выпуск включает фактическое решение модели вызвать MCP,
  проверенный вызов, результат инструмента и сводку модели по этому результату.
  Выполнение всей логики cron-скриптом вместо агентного хода не подходит.
- Сохранённые данные и отчёт переживают завершение процесса. Повторные запуски
  не должны молча выдавать одни и те же публикации за новые.
- Отчёт ссылается на статьи и отделяет описанное применение от гайда, мнения
  или рекламного обещания. Неподтверждённые сведения и заявленные авторами
  результаты не выдаются за независимо проверенные факты.
- Проверенный период без новых публикаций или без подходящих кейсов описывается
  честно. Ошибка чтения, MCP, сохранения или доставки не маскируется под
  успешный пустой или доставленный отчёт. Частичный результат после сбоя
  остаётся различимым; неопределённая доставка не считается подтверждённой.
- Адресат Telegram задаётся приложением, не моделью или текстом статей. Доступ
  MCP-инструмента ограничен задачей; секреты не передаются модели и хранятся
  по правилам проекта.
- День 18 остаётся самостоятельным `day18/`: сданный `day17/` не изменяется и
  не импортируется. Из него можно взять как образец только идею агентного
  вызова MCP и проверок harness.
