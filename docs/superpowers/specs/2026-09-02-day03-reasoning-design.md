# День 3: сравнение способов рассуждения

Дата: 2026-09-02

## Задание

Взять одну задачу и решить её через API четырьмя способами: прямой ответ; «решай пошагово»;
модель сама пишет промпт и решает по нему; группа экспертов в промпте. Сравнить ответы
и определить, какой способ дал наиболее точный результат.

## Проблема, которую решает дизайн

Задание требует сказать, какой способ **точнее**, но точность не определяет. Если взять
задачу без однозначного ответа, сравнение выродится в «этот ответ мне нравится больше».
Поэтому задача выбирается такая, где правильный ответ вычисляется кодом независимо
от модели, а сравнение считается по прогонам, а не по впечатлению.

Это продолжение дня 2, где проверка формата была машинной, а не на глаз.

## Задача

Конфигуратор FPV-дрона: собрать квадрокоптер из каталога так, чтобы он взлетел,
уложился в бюджет и продержался в воздухе как можно дольше.

Каталог **вымышленный намеренно**: на реальных названиях модель может вспомнить ответ
из обучения вместо того, чтобы вывести его.

Пять позиций: рама, моторы (4 шт), пропеллеры (комплект 4), регуляторы (4 шт), аккумулятор.

Правила:

1. Размер пропеллера совпадает с тем, на который рассчитан мотор.
2. Пропеллер такого размера влезает в раму.
3. Число банок аккумулятора совпадает с тем, на которое рассчитан мотор.
4. Регулятор держит ток мотора: `esc.max_current >= motor.current`.
5. Аккумулятор отдаёт нужный ток: `c_rating * mah / 1000 >= 4 * motor.current`.
6. **Тяга не меньше удвоенного взлётного веса**: `4 * motor.thrust >= 2 * взлётный вес`,
   где взлётный вес = рама + 4 мотора + комплект пропеллеров + 4 регулятора + аккумулятор.
7. Сумма цен не превышает бюджет.

Цель: максимальное расчётное время полёта; при равном времени — более дешёвая сборка.

### Почему выбран именно этот домен

Решающее свойство — **сцепленность ограничений**. Если правила независимы (у ПК четыре
из пяти были простым совпадением «сокет к сокету»), модель проверяет их по одному
и справляется в любом режиме — тогда все четыре режима дадут одинаковый результат
и сравнивать будет нечего.

У дрона ограничение замыкается само на себя: аккумулятор нужен большой ради времени
полёта, но он сам весит, вес поднимает порог требуемой тяги, тяга требует моторов
помощнее, те тянут больше тока и требуют аккумулятора крупнее. Круг замкнулся.
Удержать это в одном проходе трудно — именно здесь пошаговое рассуждение и должно
оторваться от прямого ответа.

Эталон считается полным перебором всех сочетаний. Не человек решает, что правильно.

## Структура

```
day03/build.py       каталог, правила, валидатор, перебор. Без API вообще
day03/reasoning.py   четыре режима, прогоны, отчёт. Здесь API
day03/test_build.py  офлайн-тесты валидатора и разбора ответа
day03/results.json   сырые результаты замера (для --report без обращений к API)
```

`build.py` не обращается к API сознательно: эталон и проверку можно гонять бесплатно
и мгновенно. Тот же приём, что `test_verdict.py` во дне 2.

## Четыре режима

| режим | что подаётся | вызовов на прогон |
| --- | --- | --- |
| `direct` | задача + формат ответа | 1 |
| `steps` | то же + «решай пошагово, рассуждай вслух» | 1 |
| `meta` | вызов 1: «составь промпт для решения». Вызов 2: сгенерированный промпт + задача | 2 |
| `experts` | то же + роли: аналитик, инженер, критик; каждый высказывается, затем общий вывод | 1 |

Режим `meta` генерирует промпт **заново на каждом прогоне**. Иначе у него был бы
искусственно заниженный разброс, и сравнение с остальными тремя стало бы нечестным.

К сгенерированному промпту всегда дописывается тот же блок про формат ответа —
модель может его не включить, а без него ответ нечем разобрать.

## Формат ответа

Свободный текст, последняя строка:

```
ОТВЕТ: cpu=K5, board=MB-A1, memory=R4-32, card=G3, power=P850, case=C-Mid
```

Инструкция про формат **дословно одинаковая во всех четырёх режимах**, иначе сравнивались
бы форматы, а не рассуждения.

Приём из дня 2 здесь неприменим: `response_format: json_object` требует, чтобы весь ответ
был JSON-объектом, а режимы `steps` и `experts` обязаны показать рассуждение и реплики
экспертов — им негде поместиться. Жёсткий формат убил бы половину эксперимента. Отсюда
компромисс: свободный текст плюс одна разбираемая строка, и разбор своим кодом.

## Измерение

Температура **1.0, не 0**. При нуле модель почти детерминирована, двадцать прогонов дадут
двадцать одинаковых ответов, и счёт выродится в 0 или 20. Разброс нужен, иначе метрика
не метрика.

Три метрики на каждый прогон:

1. **валидна** — сборка не нарушает ни одного правила совместимости
2. **в бюджете** — сумма цен не превышает потолок
3. **оптимальна** — совпала с лучшей сборкой по `score`, и насколько отстала, если нет

Отдельно считаются прогоны, где ответ **не разобрался**. Их нельзя записывать модели
в ошибку решения: это поломка формата, а не рассуждения. Та же ловушка, что во дне 2
с обрывом по `max_tokens`.

## Калибровка

Перед основным замером — 5 прогонов только режима `direct`. Если попаданий 5 из 5 или
0 из 5, задача не различает режимы и её надо крутить: менять бюджет и состав каталога
до попадания примерно в половине случаев. Только после этого основной замер.

Причина: эвал, который у всех режимов даёт одинаковый результат, ничего не измеряет.

## Прогон и производительность

20 прогонов на режим. Вызовов: 20 + 20 + 40 + 20 = **100**, плюс 5 на калибровку.

Последовательно это 30–40 минут. Поэтому:

- прогоны идут **параллельно**, пул на 8 потоков — примерно пять минут
- сырые результаты пишутся в `day03/results.json`
- флаг `--report` перепечатывает таблицу из файла **без единого обращения к API**

Последнее для записи видео: замер гоняется один раз заранее, на камере показывается
мгновенный отчёт плюс один живой прогон для демонстрации.

## Обработка ошибок

- сбой запроса к API — прогон помечается как несостоявшийся и в статистику не идёт,
  количество таких прогонов печатается отдельно
- ответ не разобрался — отдельная категория, не ошибка решения
- позиция, которой нет в каталоге — сборка невалидна, причина печатается
- если валидных сборок в каталоге нет вообще — `build.py` падает с явным сообщением,
  а не выдаёт пустой результат

## Тесты (офлайн, без API)

`test_build.py` проверяет **свою же проверку**, потому что баг в разборе иначе запишется
в ошибку модели:

- разбор строки `ОТВЕТ:` — нормальная, с лишним текстом после, другой порядок позиций,
  две строки `ОТВЕТ` (берётся последняя), markdown-звёздочки вокруг, пропущенная позиция,
  строки `ОТВЕТ` нет вовсе
- валидатор — каждое из пяти правил нарушается по отдельности и ловится
- эталон — у задачи ровно одна оптимальная сборка

## Что попадает в сдачу

- таблица: четыре режима × три метрики
- вывод, какой способ точнее и на чём именно ломаются остальные
- отдельной строкой — сколько прогонов не разобралось по формату

## Что сознательно не делается

- судья на второй модели: правильный ответ известен точно, судить нечего
- несколько задач разной сложности: задание говорит «одну задачу»
- фреймворки и внешние библиотеки: прямой API, как во дне 1 и 2
