## Контракт реализации и границы

Цель будущей реализации — самостоятельный `day18/`: cron в 18:00 `Europe/Warsaw` запускает **агента**, модель сама предлагает единственный разрешённый MCP call, harness проверяет его и возвращает structured observation, модель пишет structured draft, harness сохраняет проверенный отчёт, приложение отправляет одно сообщение в фиксированный личный Telegram-чат с **максимум двумя статьями на отчёт**. Это не лимит RSS ingestion, model analysis или всех отправок за календарный день при восстановлении очереди. Это policy-bounded внешняя коммуникация; модель не выбирает URL, recipient, secrets, tool policy или FSM transition. Один VPS, SQLite WAL на устойчивом диске, source profile `habr_ai_agents_ru_v1`; без HTTP endpoint, web-browsing статей, других источников, multipart, webhook, автодогона cron и runtime-импортов из `day17/`.

Порядок строго зависимый: **P0 каркас → P1 schema/FSM → P2 repository/invariants → P3 RSS MCP → P4 agent harness → P5 classification/report → P6 delivery queue/Telegram → P7 scheduler/VPS packaging → P8 live evidence/video**. P0 не запускает сеть; P6 нельзя начинать как внешнюю отправку до P1–P5 и crash/recovery тестов. P7 подготавливает конфигурацию/инструкцию, но реальная установка cron/VPS — отдельный финальный gate. P8 вообще не выполняется без отдельной санкции и готовых credentials. Каждый этап допускается к следующему лишь при своём stop condition; неудачный этап оставляет durable evidence и не объявляется успешным по тексту модели.

Будущие имена файлов — предполагаемая раскладка, а не созданный код: `day18/{config,models,store,fsm,repository,rss_mcp_server,mcp_client,tool_calling,agent,report,delivery,scheduler,cli}.py`, `day18/schemas/*.json`, `day18/test_*.py`, `day18/README.md`, `day18/results/` (redacted evidence), `day18/demo/` (видео лишь финально). Модули разделяют model/provider adapter, harness, MCP server, SQLite repository, scheduler entrypoint и Telegram adapter. Shared runtime imports из `day17/` запрещены; допустимо изучить поведение `day17/tool_calling.py`, `agent.py`, `store.py` и тесты как образец. В Day 17 реальны `tool_choice="auto"`, local schema/linked results и транзакционный audit, но его chat lifecycle, Git tool, FSM и бюджеты не копируются.

## Этапы

### P0. Самостоятельный каркас и typed boundaries

- **Цель/зависимости:** создать изолированный пакет Day 18 до любых side effects; зависит только от утверждённой версии плана.
- **Файлы/schema:** `day18/{config,models,cli}.py`, `day18/README.md`, offline `test_architecture.py`; SQLite schema пока нет. Типы для slot, run, model/tool attempt, batch/result, draft, report, delivery attempt, reason code и adapter protocols. Конфигурация содержит только имя env-переменных и валидируемые параметры; token/chat_id читаются приложением лишь в send boundary, их значения не сериализуются в DB/trace.
- **Шаги/инварианты:** зафиксировать dependency direction `cli/scheduler → agent → tool gateway/repository/report/delivery`; MCP server не импортирует Telegram, model adapter не получает secrets. Tool registry содержит только `collect_habr_agent_cases`; Telegram не является MCP tool. Provider закреплён проектной конфигурацией (`OpenRouter`/`deepinfra`, fallback и SDK retries отключены) либо несовместимая конфигурация fail-closed; фактическую модель/токенизатор проверить перед live gate. Отдельные injected clocks/network adapters делают offline replay возможным.
- **Тест/stop/evidence:** import/dependency scan и offline config tests доказывают отсутствие runtime `day17/`, secret literals, лишних tools и автоматического network access при импорте. Stop при изменении `day17/`, необходимости секретов в коде или дополнительного источника/tool. Recovery/rollback — удалить только ещё неиспользованный новый каркас с сохранением чужих файлов; ничего в БД/сети нет. Осталось непроверенным всё runtime-поведение.

### P1. SQLite schema и persisted FSM до сетевых интеграций

- **Цель/зависимости:** поднять durable data model и все разрешённые переходы, используя P0 types; ни RSS, ни provider, ни Telegram ещё не вызываются.
- **Файлы/schema:** `day18/{store,fsm}.py`, `day18/migrations/*.sql`, `day18/{test_store,test_fsm}.py`. Схема с WAL, FK, migrations/schema version и таблицами: `scheduled_slots`, `runs`, `run_transitions`, `model_attempts`, `tool_attempts`, `articles`, `observation_batches`, `observations`, `batch_memberships`, `source_rejections`, `classifications`, `reports`, `report_memberships`, `publication_claims` + history, `delivery_attempts`, `delivery_checkpoints`, `operator_resolutions`, `source_coverage`. Точные identities/constraints ниже; stage/reason, UTC timestamps и исходная timezone обязательны.
- **Шаги/инварианты:** одна миграция в пустую БД и upgrade fixture без уничтожения данных; `BEGIN IMMEDIATE`/CAS по `state_version` для каждого перехода и append-only event в той же transaction. Декларативная allowlist из таблицы FSM ниже; illegal transition no-op. `UNIQUE(profile, local_date, zone)` и partial `UNIQUE(slot_id)` для `origin=scheduled` делают плановый slot/run идемпотентным. Диагностический `origin=manual` имеет отдельный UUID `manual_invocation_id`, `slot_id=NULL`, `UNIQUE(manual_invocation_id)` и обязательный `no_send`; DB `CHECK` связывает допустимые пары origin/identity. Явный backfill/publication адресует **плановый slot**, не переименовывает manual run. Единый publication lease/global send gate защищает **отправку**, не запрещая другим run собирать/готовить данные. Схема хранит stage, safe reason, owner/actor, version, attempt counters и active-time ledger; active phase reservation фиксируется до вызова, settlement — после подтверждённого завершения. `DELIVERED` нельзя записать без receipt `message_id`; `DATA_READY` без committed batch; `REPORT_READY` без report/membership/claims; `SENDING` без attempt/payload hash.
- **Тест/stop/evidence:** unit transition matrix (каждый разрешённый и запрещённый edge), SQLite FK/UNIQUE/CHECK tests, manual `no-send` и scheduled run на одну дату без collision, DST slot identity, два процесса/конкурентный trigger, crash до/после commit, reopen, migration/backup dry-run на временной БД. Stop при нетранзакционном state+evidence, обходе guard SQL-операцией приложения или потере данных после reopen. Recovery/rollback — transactional migration rollback; до обновления реальной БД сделать проверяемую backup-копию, не удалять существующие records. Evidence — локальные test logs/schema version; RSS/provider/send остаются непроверенными.

### P2. Repository, identities, idempotency и recovery API

- **Цель/зависимости:** поверх P1 создать единственный write/read boundary и запросы на восстановление; только synthetic records.
- **Файлы/schema:** `day18/{repository,models}.py`, `day18/test_repository.py`; новые таблицы не предполагаются, но индексы/constraints P1 доводятся после теста queries. Article identity — canonical Habr article ID или нормализованный canonical URL; `UNIQUE(profile, canonical_article_id)`. `UNIQUE(article_id)` у immutable observation, `UNIQUE(run_id,idempotency_key)` у batch, `UNIQUE(batch_id,observation_id)` у batch membership, `UNIQUE(run_id,observation_id)` у classification, `UNIQUE(run_id)` у report, `UNIQUE(report_id,observation_id)` у report membership, active claim unique per observation, `UNIQUE(report_id,attempt_no)` при `attempt_no≤2`.
- **Шаги/инварианты:** atomically commit article/observation/batch/membership/coverage; replay по тому же run+key сначала читает committed result без RSS. `tool_call_id` хранится как identity attempt, но смена/дубликат ID не создаёт новый batch. Immutable RSS evidence не перезаписывается latest metadata; одинаковый `pubDate` разделяется canonical ID, overlap покрывает границу. Разделить source coverage, observations, report membership и delivery checkpoint как независимые записи. Query report pool исключает processed_out_of_scope, active/delivered/quarantined claims, но включает unclaimed eligible и ранее не показанные. Retry/resume читает evidence, а не верит памяти процесса; бюджеты и активные интервалы persisted, crash не обнуляет расход.
- **Тест/stop/evidence:** parallel `get_or_create`, timeout-after-commit replay, crash посередине batch transaction, tie timestamps, duplicate/edit/reappearance, unavailable receipt, old retry/new backlog overlap, deterministic replay после reopen. Stop при втором batch или observation, потерянном partial run, пересечении active claims или сдвиге checkpoint от ingestion. Recovery — reconcile по key/commit marker; если batch не доказан, оставаться failed/paused, не фабриковать success; migration rollback только из backup. Evidence — SQLite integration/fault-injection traces; реальный RSS не проверен.

### P3. Узкий RSS MCP tool

- **Цель/зависимости:** реализовать ровно один MCP server/tool поверх P2, сначала с локальными RSS fixtures.
- **Файлы/schema:** `day18/{rss_mcp_server,mcp_client,tool_calling}.py`, `day18/schemas/{collect_input,collect_output}.json`, `day18/{test_rss_mcp,test_mcp_protocol}.py`; schema DB не меняется, writes идут через P2. JSON schemas — точные input/output SPEC с `additionalProperties:false` на каждом object, проверкой `format`, семантическими guards и enums; не расширять модельный input произвольным URL/path/SQL/recipient/secret/командой.
- **Шаги/инварианты:** profile `habr_ai_agents_ru_v1` закрепляет ровно URL из SPEC (`https://habr.com/ru/rss/search/?q=%D0%98%D0%98-%D0%B0%D0%B3%D0%B5%D0%BD%D1%82%D1%8B&order_by=date&target_type=posts&hl=ru&fl=ru&limit=100`); источник задаёт приложение, HTTPS Habr host без redirect наружу и без runtime-подстановки. Discovery допускает только зарегистрированный tool. Сверять run/slot/period/zone/profile/key с trusted context и повторно на MCP boundary. Ограничить RSS ≤2 MiB, ≤100 items, read/write ≤60 s, один retry только после доказанного pre-response network failure. Безопасный XML без DTD/XXE, очистка HTML/control/bidi, canonical link/ID; сохранять title ≤240 символов и description ≤1000, отдавать title ≤512 UTF-8 bytes и excerpt ≤512 UTF-8 bytes, candidate list ≤10/≤16 KiB, result ≤32 KiB. Не fetch полного текста. Валидный ID/link при отсутствующем или невалидном `pubDate` сохраняется как observation **текущего read batch** по `read_at_utc` даже после 18:00: `published_at_utc=null`, `invalid_entries` увеличен, `in_period` не увеличен, coverage минимум `partial_coverage`; candidate помечен «дата неизвестна» и доступен модели в P5. Broken ID/link отдельно сохраняет bounded source rejection, а не молча отбрасывает весь batch. Сначала atomic commit batch/items/coverage, потом `success_*`/`partial_coverage` result; errors возвращают safe reason, committed batch при replay не перечитывается.
- **Тест/stop/evidence:** RSS fixtures для пустого feed, no-new, deterministic out-of-profile, no-confirmed-only-after-model, 100-item cap, oversize, parse gaps, outage, malformed link/ID, missing/invalid pubDate после 18:00, equal timestamp, edit/reappearance, injection, fake tool call, redirects/XXE. Для date fixture проверить persisted observation с `published_at_utc=null`, batch membership текущего чтения, `invalid_entries`/partial coverage, наличие кандидата в P5 и отсутствие false empty/no cases; для broken ID/link — source rejection/partial без потери валидных соседних items. Успех с items, empty, no_matching, partial, source/storage/invalid_request различаются и связаны с batch evidence. Stop при невалидном schema/result, ложном `success_empty`, результате до commit или нарушении idempotency; rollback — transaction rollback и safe error, committed result сохраняется. Evidence — offline protocol+SQLite integration; live RSS URL/охват остаётся launch gate.

### P4. Agent entrypoint и первая половина bounded loop: model→MCP

- **Цель/зависимости:** P0–P3 готовы; agent entrypoint запускает модель, а не заменяющий её worker. Первый provider call с `tool_choice=auto`; отсутствие разрешённого call → `FAILED_BEFORE_DATA`. Этап заканчивается на проверенном `DATA_READY` или failure: путь второго model call **закрыт до P5**, где появятся preflight и draft validator.
- **Файлы/schema:** `day18/{agent,tool_calling,cli}.py`, `day18/{test_agent_loop,test_budgets}.py`; DB schema не меняется, заполняются model/tool attempts, transitions и usage/cost (только если provider сообщил).
- **Шаги/инварианты:** discovery перед model-visible catalog; provider envelope разбирается по каждому call ordinal и исходному ID, duplicate/missing IDs получают synthetic audit identity, но **ровно один** linked structured result на каждый call. Mixed/multiple, unknown tool, malformed/extra args, mismatch trusted context и повторный call получают denial result без MCP; локальный audit сохраняет result, даже если следующий provider call запрещён. Разрешённый call исполняется только после permission+budget check; tool result валидируется как schema+committed batch semantics и ограничивается. Обычный attempt зарезервирован для ≤2 model calls/≤1 RSS MCP execution, но P4 исполняет только первый call; explicit operator resume максимум второй generation attempt, ≤4/≤2 за run, committed batch reuses без RSS; максимум одна reconciliation тем же key без нового RSS после неопределённого MCP исхода; SDK/model retries=0. Provider ≤180 s/call, model call 1 ≤1000 visible output tokens; для будущего call 2 закреплён потолок ≤20000, но invoke запрещён до P5. Active generation ≤480 s/attempt и ≤960 s/run; tool result/candidates/article limits из P3. Для каждого активного provider/MCP/validation interval **до начала** в SQLite резервировать не больше phase cap и остатка attempt/run: provider 180 s, MCP 60 s, validation суммарно 60 s/attempt; после доказанного окончания settlement по monotonic elapsed, а после crash незакрытая reservation целиком списывается как bounded worst-case (не календарный downtime). Перед возможным Telegram request аналогично резервируется ≤15 s в отдельном dispatch budget P6. Persist counters и phase evidence, crash не обнуляет расход; persisted idle/queue age вообще не входит в ledger. Hidden reasoning/raw RSS/secret не писать в trace. Если provider учитывает hidden reasoning в общем cap, перед P5 вычислить и вычесть измеренную верхнюю границу; если безопасный visible budget неизвестен, не делать второй вызов.
- **Тест/stop/evidence:** fake provider + настоящий локальный MCP protocol доказывают только tool proposal→validation→execution/denial→linked result→`DATA_READY`, отсутствие call, duplicate IDs, multiple/unknown/repeat, malformed result, crash/replay, exhausted budgets; assertion `model_call_count≤1` в P4. Fault test: crash во время provider/MCP, restart через `>960 s`; ledger списывает не больше reserved phase cap, downtime не списывает и не сбрасывает прежний расход. Stop текущего этапа при обходе permission, втором вызове до P5 или неполном linked result; если позднее в P8 нет настоящего model-proposed MCP в live trace, остановить launch. Rollback — сохранённый failure/stage/reason, без false report. Evidence offline unit/integration; **real-model tool choice** и оплачиваемые вызовы — отдельный P8 gate, не результат mock.

### P5. Classification, capacity preflight и атомарный report

- **Цель/зависимости:** P4 заканчивается на committed aggregate/`DATA_READY`; только P5 после capacity preflight открывает второй provider call. Модель классифицирует только очищенные RSS fields, harness сохраняет проверенную сводку до внешней доставки.
- **Файлы/schema:** `day18/{report,models}.py`, `day18/schemas/draft.json`, `day18/{test_report,test_capacity}.py`; DB schema P1 используется, report/classification/membership/claim/state commit обязаны быть одной transaction.
- **Шаги/инварианты:** report pool объединяет новый batch с oldest eligible backlog без смешения feed counts; до model call 2 выбирать max `model_seen≤20` по **полному worst-case compact JSON** ≤18432 escaped UTF-8 bytes и available visible-token budget закреплённого provider. При отсутствии точного tokenizer — консервативно 1 token/byte +1024 margin; `proposed_text≤1024` bytes, `summary≤256`, ≤1 metric `{text≤160,attribution≤120}`, evidence_refs≤3, category/ID/outcome/coverage и прочие обязательные поля входят в расчёт. Если hidden-reasoning share неизвестен или не помещается один имеющийся кандидат, `FAILED_AFTER_DATA/budget_exhausted` без call 2; пустой pool допускает валидный нулевой draft. Выбор до 15 new/5 backlog, при уменьшении мест попеременно и по детерминированному порядку; если `model_seen≥2` и обе очереди непусты, каждая получает хотя бы одно место; omitted остаются unclassified backlog. Draft entries должны точно покрывать `model_seen` и проходить strict schema, grounding IDs/links/evidence/metric attribution и outcome guards; `confirmed_described_case` требует конкретную рабочую или личную задачу+роль/действие агента+признак применения в RSS, иначе possible/guide/opinion/advertisement/tool_news/not_relevant. `empty_feed`, `no_confirmed_cases`, partial coverage и source error не смешивать. В одной transaction записать все dispositions, immutable report/membership/display flags/claims и `REPORT_READY`; payload ≤3500 символов строит harness из модельных summaries+trusted counts/links, не из выбранного моделью recipient. Нулевой report тоже sendable.
- **Выбор двух статей:** после классификации оставить полный relevant membership immutable, но детерминированный renderer помечает `displayed_in_payload` максимум у двух: сначала `confirmed_described_case` (реальный бизнес-процесс, действия агента, внедрение/пилот по RSS evidence), затем при свободном месте `possible_case` с явной пометкой неопределённости. Внутри категории сначала oldest backlog, затем новые; гайды/мнения/реклама/tool_news не занимают article slots. Остальные relevant members увеличивают `payload_omitted`, после подтверждённой доставки возвращаются в backlog; `model_seen≤20`, batch/coverage и число сохранённых observations не обрезаются до двух. Intro `proposed_text` не может протащить третью статью/ссылку. В P5 до `REPORT_READY` проверить `payload_displayed≤2` и соответствие persisted payload, flags и hash.
- **Тест/stop/evidence:** end-to-end **offline** fake-model→real-local-MCP→fake-model trace доказывает второй call только после preflight; конструктивный max-field fixture для выбранного `model_seen`, provider-tokenizer check отдельно от synthetic bound, truncation/oversize rejection, 40 guides over runs + новый кейс, 15+5 progress, unsupported claim/link, partial/empty matrix, crash по обе стороны report commit и после commit до dispatch. Stop при stranded report, ложной классификации от tool, model output без validation, report без immutable membership или candidate preflight после provider call; recovery — committed `REPORT_READY` dispatch без модели, неcommitted draft → `FAILED_AFTER_DATA`/operator resume, observations остаются backlog. Evidence unit+SQLite integration+replay; real-model качество классификации ещё P8.
- **Тест нового лимита/stop:** fixtures 3 confirmed + 1 possible, 1 confirmed + 2 possible и 0 confirmed + possible доказывают ≤2 article IDs/links в одном payload, приоритет confirmed и явную пометку possible; третий link в `proposed_text` отклоняется. Проверить сохранение полного membership, `payload_omitted`, возврат не показанных в следующий отчёт без дублей и отсутствие влияния на ingestion/coverage. Stop при третьей статье, неверной категории, потере omitted или расхождении payload hash/flags; evidence — renderer unit + SQLite restart/queue integration, live quality отдельно P8.

### P6. Глобальная очередь и Telegram adapter

- **Цель/зависимости:** P1–P5, включая fault injection, зелёные; только потом возможно внешнее сообщение. Пока используются fake Telegram transport и configured recipient fingerprint, не реальные token/chat_id.
- **Файлы/schema:** `day18/{delivery,repository,cli}.py`, `day18/{test_delivery,test_queue}.py`; таблицы P1 дополняются только migration при доказанной необходимости. Token берётся только в adapter из защищённой config на send boundary, chat_id — только фиксированный config, в DB лишь fingerprint.
- **Шаги/инварианты:** dispatcher на каждом entrypoint **до нового slot**, после `REPORT_READY` и operator resolution выбирает oldest sendable report даже с пустым membership; global gate запрещает `SENDING`, пока unresolved `DELIVERY_UNKNOWN`, старший failed-send report или чужой sender. Один active publication sender; другие run могут готовить report. `SENDING`/attempt/payload hash/recipient fingerprint коммитятся **до** запроса. Один plain-text/escaped Telegram payload ≤3500 символов без multipart, полный membership frozen, displayed count и omitted count persisted. На Bot API success нужен `message_id` для `DELIVERED`; это приём API, не прочтение. Доказанный pre-send failure → `FAILED_BEFORE_SEND`, допускает ≤1 automatic retry при общем cap 2 attempts/report; definitive rejection → `DELIVERY_FAILED`, повтор только explicit operator с proof и оставшимся cap; 5xx/timeout/connection loss после request boundary → `DELIVERY_UNKNOWN` без auto retry. Unknown резервирует все members, не двигает checkpoint и блокирует следующие sends; operator resolution с actor/time/reason/evidence: подтверждённый `message_id` → delivered, authoritative negative acknowledgement → failed, иначе quarantine без resend и без освобождения claims/checkpoint. Retirement делает старый payload навсегда non-sendable, released observations доступны только будущему unfrozen report. Dispatch active budget ≤60 s/report, HTTP ≤15 s/attempt, persisted ожидание очереди не расходует generation/dispatch budget.
- **Guard adapter:** перед каждым send сверить persisted payload/hash/`displayed_in_payload` и ≤2 уникальных article references, включая вводный абзац; при нарушении не посылать и сохранить safe failure. Retry не перегенерирует текст или иной набор двух. Если в один календарный день после восстановления очереди уходят несколько разных отчётов, лимит двух действует для каждого отчёта, не как глобальная дневная квота.
- **Тест/stop/evidence:** fake adapter matrix pre-send/definitive rejection/5xx/timeout/receipt, overlapping senders, crash до/после `SENDING` request marker, lost receipt, global gate, unknown→quarantine/confirmed/negative proof, old retry vs newer report, checkpoint gaps, displayed/omitted, очередь после паузы >960 s без новых model/MCP calls. Stop при отправке до report/attempt commit, авто-retry unknown, обходе cap 2, смене recipient из RSS или secret leakage; recovery — после возможного request без receipt только unknown, lease expiry не доказательство недоставки; report/observations не удалять. Evidence local fault injection; **реальный Telegram receipt** только P8.
- **Тест cap при recovery:** два ready reports отправляются в одни местные сутки, в каждом ≤2 статьи; при retry первого payload/hash и выбранные article IDs неизменны. Omitted после receipt остаются доступными только будущему unfrozen report; fake adapter и SQLite assertions отделены от реального Telegram receipt.

## FSM и атомарные границы

Состояния и guards ниже — **контракт реализации** из SPEC, не альтернативная FSM Day 17. `DELIVERED` terminal. Ошибочные состояния paused/nonterminal до explicit action; retirement — durable terminal flag для sendability, quarantine — durable operator resolution при остающемся `DELIVERY_UNKNOWN`, а не молчаливое переименование в `DELIVERED`. Обычный cron не меняет terminal/paused run. Все разрешённые переходы выполняются transaction+CAS с append-only transition/evidence; запрещённый edge не меняет ни state, ни side effects.

| State | Durable evidence и разрешённые переходы | Guard / retry / crash recovery / оператор |
|---|---|---|
| `STARTED` | slot+run+version → `MCP_PENDING` / `FAILED_BEFORE_DATA` | nonterminal; один run/slot; crash возвращает к entry guard, no secret/network inference; operator inspect |
| `MCP_PENDING` | model/tool attempts, trusted request/key → `DATA_READY` / `FAILED_BEFORE_DATA` | nonterminal; model-proposed valid call, linked result, batch commit FK; после crash сначала reconcile key, максимум одна reconciliation без RSS; no batch → failure/operator resume |
| `DATA_READY` | committed batch FK+coverage → `REPORT_PENDING` / `FAILED_AFTER_DATA` | nonterminal; нельзя без commit; reopen uses same immutable batch, no RSS retry; operator inspect partial |
| `REPORT_PENDING` | second model attempt/draft status → `REPORT_READY` / `FAILED_AFTER_DATA` | nonterminal; preflight до provider, strict validated draft; report+classifications+membership+claims+state atomic; crash до commit не оставляет report, после commit уже READY |
| `REPORT_READY` | validated report FK, immutable membership/payload hash → `SENDING` / `FAILED_BEFORE_SEND` | nonterminal; oldest sendable + global gate + active lease + budget; crash/restart dispatch без model/MCP; operator may defer |
| `SENDING` | persisted send attempt+payload hash+recipient fingerprint+request boundary → `DELIVERED` / `DELIVERY_FAILED` / `DELIVERY_UNKNOWN` | nonterminal; receipt `message_id` / definitive rejection / possible request respectively; crash after request boundary без durable receipt → UNKNOWN, никогда автоматический resend |
| `DELIVERED` | receipt `message_id`, claim disposition, contiguous checkpoint | terminal; no cron transitions; operator audit only, user read receipt не утверждается |
| `FAILED_BEFORE_DATA` | stage/reason/attempt → `MCP_PENDING` лишь explicit resume | paused; максимум второй generation attempt, key тот же; после исчерпания остаётся gap/operator inspect |
| `FAILED_AFTER_DATA` | batch FK+stage/reason → `REPORT_PENDING` лишь explicit resume | paused; reuse committed batch, не повторять RSS; после budget exhaustion observations unclaimed backlog |
| `FAILED_BEFORE_SEND` | report FK+proof no request bytes left → `REPORT_READY` при cap или retirement | paused; ≤1 automatic retry только proven pre-send; после cap оператор retirement, не терять claims до него |
| `DELIVERY_FAILED` | report+definitive rejection или authoritative negative proof → `REPORT_READY` только explicit operator retry при cap, иначе retirement | paused; отсутствие receipt/5xx/UI absence не proof; checkpoint unchanged |
| `DELIVERY_UNKNOWN` | report+attempt+request-start без reliable receipt; operator → `DELIVERED` с verified `message_id` / `DELIVERY_FAILED` с authoritative linked negative proof / quarantine resolution при сохранении UNKNOWN | blocked; no auto retry; actor/time/reason/evidence required, quarantine clears gate but reserves members и не двигает checkpoint |

| Crash boundary | Durable state после reopen | Разрешённое продолжение / запрещённое |
|---|---|---|
| до batch commit («ничего не сохранено») | `MCP_PENDING`+attempt либо `FAILED_BEFORE_DATA`, batch отсутствует | key reconciliation, затем explicit second attempt по cap; нельзя `DATA_READY` или success без commit |
| после batch commit, до/после tool response | committed batch+coverage, possibly `MCP_PENDING` | replay возвращает saved aggregate по key; затем `DATA_READY`; нельзя второй batch/RSS при доказанном commit |
| до report transaction commit | `REPORT_PENDING` или `FAILED_AFTER_DATA`, no report/claims | explicit allowed resume при budget, observations unclaimed; нельзя `REPORT_READY` по одному тексту модели |
| после report transaction commit, до dispatch | `REPORT_READY`+immutable report/claims | следующий entrypoint dispatch oldest ready без model/MCP, включая empty membership; нельзя потерять report |
| после `SENDING` commit, до доказанного pre-send boundary | attempt+payload hash; если строго доказано, что request не начался | `FAILED_BEFORE_SEND`, второй attempt только по cap; без доказательства → UNKNOWN |
| после начала HTTP request, до receipt commit | `SENDING`+request-start+attempt | `DELIVERY_UNKNOWN`, global gate; lease expiry/timeout/UI absence не разрешают resend |
| после receipt+`DELIVERED` commit | `message_id`, delivered claims и checkpoint до непрерывного slot | terminal, повтор trigger возвращает существующий run; нельзя повторить send |
