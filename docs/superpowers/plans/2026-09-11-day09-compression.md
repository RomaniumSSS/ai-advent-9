# День 9 — сжатие истории

## Согласованные требования

Два сценария: планирование проекта и обычная беседа с предпочтениями.
Два режима рядом: полная история и summary с последними сообщениями.
Модель по умолчанию для диалога и summary — DeepSeek V4 Flash,
ключ каталога `deepseek-v4-flash`. Перед платным прогоном проверить доступность
ID и тарифы API. Роман утвердил общий бюджет $0.50 на реальные проверки и видео.
По 3 парных прогона каждого сценария: 192 обычных вызова и примерно 12 summary
при успешных ходах. Сначала по одной паре сценария для диагностики, затем повторы.
В runner необходимо реализовать проверку бюджета перед каждым API-вызовом;
одна запись бюджета в плане расход технически не ограничивает.
День 8 сдан и находится в main; реализация самостоятельная в `day09/`.

Задание: хранить последние N сообщений целиком, старые заменять отдельным
summary в запросе; сравнить качество и токены; результат — код и видео.

## Технические решения

- Полная переписка остаётся архивом SQLite и источником отображения в панели.
  Активный контекст: исходный system → summary в роли assistant с явной
  пометкой исторических данных → последние сообщения → новый вопрос.
  Summary не становится новым системным правилом.
- По умолчанию сохраняются 6 сообщений (3 полных хода). Перед очередным
  запросом сжимаем, если перед свежим хвостом накопилось 10 сообщений.
  Оба значения чётные, положительные, настраиваемые; пары не разрываются.
- Вход суммаризатора: предыдущий summary + ещё не сжатая старая часть.
  Системный промпт суммаризатора требует сохранять факты, числа, актуальные
  решения, ограничения и незакрытые вопросы; явно различать слова пользователя
  и предложения ассистента. Исправленные значения помечать отменёнными.
- Summary ограничено 600 токенами по локальной оценке; потолок генерации — 2000
  выходных токенов. Ориентир итогового промпта — до 120 слов. Первоначальные 200 слов давали
  пересказы больше 600 токенов и переносили предложения ассистента в требования;
  исходные прогоны сохранены, итоговые повторяются отдельно.
  Локальный счёт приблизительный, фактический расход берётся из usage.
- SQLite хранит summary и число покрытых сообщений одной транзакцией.
  Успешное сохранение предшествует замене рабочего состояния в памяти.
  Архив не удаляется. Сессии изолированы, база дня 9 отдельная.
- Пустое, обрезанное, слишком длинное или не уменьшающее контекст summary
  не применяется. Ошибка записи тоже оставляет прежний контекст.
  Ошибка видна; диалог можно продолжить с прежним контекстом, если он помещается.
- Журнал вызовов различает chat и summary. Неудачная оплаченная попытка
  сжатия входит в общий расход. Неизвестный usage не подменяется нулём.
- Панель: единое поле отправляет один вопрос в оба режима; обе стороны имеют
  независимые сессии, одинаковую модель и исходный system. Видны архив,
  summary, число активных сообщений, события сжатия, расход по типам и итог.
  При ошибке одной стороны повтор не должен незаметно удваивать успешную.

## Сравнение и приёмка

Два воспроизводимых сценария с фиксированными вопросами: проект (срок,
бюджет, исключённая функция и изменённое решение) и беседа (предпочтения,
ограничения и их исправления). В каждом — минимум два сжатия и контрольные
вопросы после них. Ответы режимов могут различаться; буквальное совпадение
текста не является критерием качества. Эталонные факты записываются до прогона.

Отдельно измеряем: вход каждого вызова API, суммарный вход, выход,
вход+выход всех chat и summary, фактическую цену при наличии usage.cost.
Уменьшение одного запроса не выдаём за экономию всего эксперимента.
Вход до/после на одинаковой истории — локальная оценка с явной пометкой;
сравнение двух живых диалогов учитывает различия ответов.

Готово, когда:
- [x] Сборка запроса исключает архивную часть и сохраняет свежие пары дословно.
- [x] Повторное сжатие, изоляция сессий и перезапуск проверены без API.
- [x] Отказы summary, ошибки сохранения и учёт оплаченных попыток проверены.
- [x] Оба режима и сценария доступны в панели; визуальная проверка трёх ширин.
- [x] Реальные результаты обоих сценариев сохранены без ручной подмены.
- [x] Контрольные факты оценены явно; потерянные и выдуманные отмечены.
- [x] На длинном сценарии показано снижение общего расхода с учётом summary;
      если его нет, разобрать причину и не заявлять достигнутую экономию.
- [x] Короткий участок показывает накладные расходы без обещания экономии.
- [x] README описывает запуск, механизм, замеры и ограничения; подготовлено видео.
