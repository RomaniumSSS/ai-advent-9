# Day25 — план повышения надёжности памяти

Основа: [дополнение к SPEC](../specs/2026-10-04-day25-memory-reliability.md), [исходный план](2026-10-04-day25-rag-chat.md), [задачи](../tasks/2026-10-04-day25-memory-reliability.md). Исторический A1 FAIL сохраняется.

## Подход

1. Сначала по сохранённым трассам разметить, где именно ломается цепочка: выбор режима вопроса, поисковый запрос, выдача, передача чанков или ответ. Не объявлять любой сбой памяти ошибкой только регулярного выражения.
2. В `conversation.py` заменить разрозненное распознавание продолжения на один ограниченный результат анализа запроса: режим `continuation` / `new_topic` / `explicit_filter` / `ambiguous`, основание выбора, использованные поля task state и построенный запрос. Начать с правил на явные сигналы и отрицательные случаи; без дополнительного вызова модели на каждый вопрос. При неоднозначности сохранить безопасное поведение M1. `temporal.py` получает только адресные изменения, если новые трассы покажут ошибку диапазона.
3. В контексте ответа отдельно передавать подтверждённые пользовательские факты и доступные документальные чанки. Предложения ассистента остаются историей, а не пользовательским выбором. На границе успешного ответа проверять атрибуцию конкретных заявлений о выборе пользователя; при неуверенной классификации не выдавать непроверенное утверждение как факт. Если надёжная локальная проверка невозможна, использовать ограниченный шаблон/запрос на уточнение, а не общий запрет слов.
4. Сначала адресные и интеграционные офлайн-проверки, включая скрытые от реализации новые формулировки. Затем только в согласованном бюджете — два свежих живых сценария, независимая смысловая оценка и обновление отчёта. Нельзя подменять этот этап повтором сохранённого контекста.

## Этапы и контроль

| Этап | Выход | Gate | SPEC |
| --- | --- | --- | --- |
| P0 | Матрица причин по существующим 2×15: вопрос, состояние, выбранный режим, запрос, выдача, ответ; без приватного текста в публичных docs | Каждому FAIL присвоен наблюдаемый этап или `не установлено`; гипотезы отделены от фактов | M1–M3 |
| P1 | Единый выбор режима вопроса и сбор поискового запроса; диагностика; совместимость с существующим состоянием | Regression и новые отрицательные случаи: продолжение наследует нужное, новая тема и явный фильтр не наследуют лишнее; каждый ход ищет | M1–M2, M4; B1 |
| P2 | Раздельная атрибуция пользовательского состояния и документов; ограничение неподтверждённых «ты выбрал» | Неверное приписывание не получает успешный ответ; подтверждённый выбор сохраняется; цитаты, отказы и scope не ослаблены | M2–M4; B2 |
| P3 | Проверка полного пути и, при разрешённом бюджете, новые 2×10–15 в UI | Офлайн regression + holdout; потом независимый live semantic gate B3 и budget gate B4. До live — статус `NOT PROVEN` | Все; B1–B4 |

После каждого этапа отдельный сверщик сравнивает изменение со SPEC и этим планом; FAIL и обязательный NOT PROVEN возвращаются на исправление. Общий worktree редактируется последовательно. Дополнительный платный вызов, commit, push и замена существующего видео не следуют из этого плана автоматически. Бюджет, уже выделенный на прежние сценарии и ручной чат, не трактуется как разрешение на новые автоматические прогоны.

## Условие остановки

Если P0 показывает, что причина лежит в недостатке корпуса или непредсказуемом выводе модели и P1–P2 не устраняют её офлайн, не расширять правила вслепую: сохранить наблюдение, оценить минимальную следующую меру. Если новый живой B3 содержит обязательный FAIL, A1 остаётся FAIL, даже если средний результат улучшился.
